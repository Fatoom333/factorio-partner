# Как проверяем

Четыре уровня: юнит-тесты Lua без игры, юнит-тесты Python, живые тесты на сервере Factorio без окна и
сквозные сценарии. Вдобавок есть проверка с живым игроком — то, что на сервере без окна не воспроизвести
([E2E.md](E2E.md), «Финал с игроком»).

## 1. Юнит-тесты Lua (без игры)
- `mod/tests/*.lua` под `lupa`; раннер `python tools/run_lua_tests.py` из корня репозитория (зависимость
  `lupa` в `tools/requirements-dev.txt`, ставить в виртуальное окружение).
- **Версия Lua как в Factorio — 5.2**: раннер берёт `lupa.lua52`; если в сборке lupa её нет —
  `lupa.lua53` и тест-проверка, что код не зависит от целочисленного подтипа
  (`math.type`, `tostring(3.0)`, `//`).
- Раннер ставит `package.path = "<mod>/?.lua;<mod>/?/init.lua;mod/tests/?.lua"` и загрузчик,
  который превращает `scripts.core.err` в `scripts/core/err.lua`.
- Заглушки API игры — `mod/tests/stubs.lua`: `game`, `storage`, `defines` (нужные константы),
  `prototypes`, `script` (`on_event` с фильтрами, `on_nth_tick`, `on_init`, `on_load`,
  `register_on_object_destroyed`, `raise_event`), `commands.add_command` (хранит обработчик; тест
  вызывает его с `{name, tick, player_index=nil, parameter=json}`), `rcon.print` (пишет в буфер),
  `helpers.table_to_json`/`json_to_table` (через Python `json`), `serpent.line/block`, `log`,
  `settings.global`. Фабрики фейковых `LuaEntity`/`LuaSurface`/`LuaForce` — там же. Дополнительные
  заглушки под отдельные области лежат в `mod/tests/stubs_<область>.lua` и подключаются тестами этой
  области.
- Тест — файл, который `error()` при провале; раннер печатает итог и код выхода.

## 2. Юнит-тесты Python
- `server/tests/` под `pytest` (+ `pytest-asyncio`), фейковый RCON-сервер
  `server/tests/fake_rcon.py`: отвечает заготовленными конвертами, умеет терять ответ,
  отвечать вразнобой, задерживаться (для проверки повторов по `id`).
- `tools/pc/tests/` — офлайн-тесты стенда и сценариев (без игры).
- `agents/tests/` — проверка агентского слоя (`agents/lint.py`, запуск).

Запуск (в виртуальном окружении с зависимостями из `server[dev]`):
```
cd server && python -m pytest -q
cd tools/pc && python -m pytest -q
python -m pytest -q agents/tests        # из корня
```

## 3. Живые тесты на сервере без окна
- `tools/pc/run-live.ps1 -Slot N -Scenario <имя>` — запускать **из PowerShell** (Windows OpenSSH):
  ssh из Git Bash не видит ssh-agent Windows (ключи из менеджера паролей) и получает `Permission denied`.
  1. собирает zip модов, которые объявил сценарий (`MODS = [...]`, по умолчанию
     `["factorio-partner"]`; ключ `-Mods` сильнее);
  2. по SSH (`pc`) разворачивает во временной папке `fp-live-<N>` сервер без окна на **копии**
     (`Copy-Item`, не жёсткая ссылка) тестового сейва; другой сейв — ключом `-Save`. Моды ставятся
     жёсткими ссылками, `auto_pause:false`, всё слушает `127.0.0.1`, RCON `27100+N`, игра `34200+N`;
  3. запускает сценарий на ПК через `tools/pc/live_client.py`;
  4. `/quit`, забирает `results-<N>.json` и журнал, удаляет папку.
- Рабочий сейв стенд не трогает даже на чтение.
- **Пароль RCON** генерируется на ПК в файл слота (одна строка без пробелов), в git и `results`
  не попадает. Factorio печатает его в `factorio-current.log` (`Program arguments`), поэтому журнал
  выносится и печатается только вычищенным (`Copy-RedactedLog`). Известное ограничение: пока сервер
  работает, пароль виден в командной строке `factorio.exe` локальным процессам ПК (передать файлом
  нельзя); смягчение — одноразовый пароль, только `127.0.0.1`, сервер живёт минуты на копии сейва.
- Тестовый мод `mod/partner-test` регистрирует свой `/partner` с операциями `hello` и `e_*`
  **только когда `factorio-partner` выключен** (две регистрации одного имени конфликтуют).
  Операции `e_*` — только для стенда; сценарии `e_*` объявляют `MODS = ["partner-test"]`.
- **`live_client.py` — единственная точка отправки**: принимает только конверт (dict), сам
  добавляет префикс `/partner `; строки, начинающиеся с `/`, отвергает (исключение — отдельная
  функция `quit()`). `/c`, `/sc`, `/silent-command` в стенде запрещены.
- Слот — число 0..9: у каждого слота своя папка и свои порты, поэтому несколько прогонов не мешают друг
  другу.
- Сценарий — `tools/pc/scenarios/<имя>.py` с функцией `run(client) -> dict` (`{"ok": bool, ...}`); файлы `_*`
  загрузчик пропускает (общие помощники сценариев). Офлайн-тесты сценариев — `tools/pc/tests/test_*.py`.
  В ответах сценарии считают `{}` и `[]` равными.
- Ключи `tools/pc/pc.local.json` (в git не идёт): `server_python` — Python с установленным пакетом
  сервера (для сценариев через настоящий MCP-сервер); `forge`, `forge_home`, `forge_profile` — код,
  данные и профиль forge на ПК (без них `e2e_forge` честно отвечает `forge_unsupported`).
- `RUNNER = "server"` в сценарии — шаги идут через настоящий пакет `factorio_partner`
  (`server_client.py`), а не напрямую по RCON.
- `log_must_not_match` — список шаблонов; сценарий проваливается, если журнал сервера игры после
  прогона содержит хоть один (ошибки мода, рассинхронизация).
- `run-live.ps1 -Local` — сценарий исполняется на машине разработчика, игра по-прежнему на ПК, RCON
  пробрасывается SSH-туннелем.
- Подробности стенда — `tools/pc/README.md`.

## 4. Сквозные сценарии
«Поставь добычу» тремя путями: (а) чертёж из `partner_plan`; (б) призраки уже стоят (имитация рамки
Mining Patch Planner) → `build_ghosts`; (в) помощник сам размечает руду (`plan_mining`) и ведёт ленту
(`plan_belt`). Плюс проверка MCP-сервера с настоящим модом и перекладка ленты. Описание, подготовка и
запуск — [E2E.md](E2E.md).

## Проверка с игроком
То, что на сервере без окна не проверить: смерть от урона и возрождение, срабатывание `flee`/`watch`,
режим `robots` с настоящими дронами, тело второго клиента, запуск агентского слоя, вода с отсыпкой.
Стенд не умеет перезагружать сейв внутри сценария, поэтому рефлексы и миграции после перезагрузки тоже
проверяются вручную. Порядок — [E2E.md](E2E.md), «Финал с игроком».
В конце один `/c` на **копии** сейва: игра должна предупредить про достижения (значит, до этого они
были включены).
