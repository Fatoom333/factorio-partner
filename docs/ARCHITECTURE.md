# Архитектура

Как устроена система: из чего она состоит, как команда идёт от агента к телу в игре и как событие
возвращается обратно. Контракты — [PROTOCOL](PROTOCOL.md), [ACTIONS](ACTIONS.md), [EVENTS](EVENTS.md),
[STATE](STATE.md), [MCP](MCP.md); почему выбрано именно так — [DECISIONS](DECISIONS.md).

## Общая схема

```
агент (Claude, .claude/agents/partner.md)
   │  инструменты partner_*  (MCP, stdio)
   ▼
MCP-сервер (server/factorio_partner)  ── проверка аргументов, ключ помощника, курсоры событий
   │  RCON, 127.0.0.1:  /partner <JSON>   (два соединения: cmd и poll)
   ▼
мод (mod/factorio-partner)  ── очередь задач, действия, рефлексы, восприятие, буфер событий
   │  API Factorio: персонаж без клиента (или персонаж второго игрока)
   ▼
сейв игрока
```

Один сервер обслуживает всех помощников; у каждого помощника свой id, ключ, очередь задач и курсор
событий. Агент на помощника запускается отдельно (`agents/launch.py`).

## Компоненты

### Мод `mod/factorio-partner/`
Lua, Factorio 2.0. `control.lua` — точка входа: регистрирует модули в ядре одной строкой на модуль
(действия из `scripts/actions`, остальное — «модули»). Отсутствующий файл из списка — ошибка сборки
мода, а не молчаливый пропуск.

| Папка | Что внутри |
|---|---|
| `scripts/core/` | ядро: `dispatch` (команда `/partner`, конверт v1, идемпотентность через `recent`, лимиты), `init` (регистрация модулей, склейка событий, жизненный цикл), `jobs` (очередь задач и `ctx` действий), `registry` (помощники: `helper_spawn/remove/list`, смерть и исчезновение тела), `owner` (хозяин), `events` (кольцевой буфер событий), `reflexes` (операция `reflexes` и вызов проверок модулей), `ops` (`hello`, `say`), `wait`, `blobs` (`blob_put`: большие данные частями), `reserve` (резервы предметов и областей между помощниками), `schema` (проверка аргументов по схеме), `target` (поиск цели действия), `vis` (что считается видимым), `migrate` (схема `storage` и миграции), `attach` (тело — персонаж второго клиента), `nameplate` (подпись над телом и метка на карте), `bgcraft` (фоновый крафт и `craft_done`), `tidy` (автосортировка инвентаря) |
| `scripts/actions/` | действия, которые ставятся в очередь (`act`): `walk`, `approach`, `follow`, `mine`, `craft`, `insert`, `extract`, `collect`, `pickup`, `place`, `rotate`, `set_recipe`, `build_blueprint`, `build_ghosts`, `deconstruct`, `plan_mining`, `plan_belt` |
| `scripts/perception/` | операции чтения (без очереди): `state`, `map`, `resources`, `stock`, `ghosts`, `recipes`, `vision`, `rates`, `find`, `access`, `supply`, `lookup`; `tiles` — свойства плиток из игры, общие для `map`, `access`, `plan_mining` |
| `scripts/reflexes/` | рефлексы, которые срабатывают без участия агента: `flee` (атака, здоровье, отступление и возврат к делу), `death` (смерть и возрождение; включён всегда), `ammo` (заправщик турелей), `shoot` (стрельба в бою); `common` — состояние рефлексов и поиск врагов |
| `scripts/lib/` | общие библиотеки: `path` (путь и подход к цели), `inventory` (перенос предметов), `build` (общая часть стройки), `beltpath` (слой игры для прокладки лент) |
| `scripts/vendor/` | чужой код с лицензиями: `mpp` (раскладки Mining Patch Planner и переходник `partner/adapter.lua`), `router` (решатель Wuastbude Belt & Pipe Router) |
| `settings.lua`, `locale/` | настройки мода (хозяин `partner-owner`, имя помощника `partner-helper-name`, …) и тексты |

Рядом: `mod/partner-test/` — тестовый мод стенда (свой `/partner` с операциями `e_*`, регистрируется
только когда основной мод выключен), `mod/tests/` — юнит-тесты Lua.

### Модульный интерфейс (Lua)
Модуль в `scripts/{actions,perception,reflexes,lib}/` возвращает таблицу `M`:
- `M.name`, `M.schema`, `M.start/tick/stop` — действие ([ACTIONS.md](ACTIONS.md));
- `M.ops = { <op> = function(args, ctx) -> data }` — операции чтения; ошибки —
  `require("scripts.core.err").raise(code, text)`;
- `M.reflexes = { <type> = { schema = {...}, check = function(helper_id, entity, params, tick) end } }` —
  ядро зовёт `check` раз в 10 тиков для каждого живого помощника под `pcall`; быстрые реакции на урон —
  через `M.events[on_entity_damaged]`;
- `M.events = { [defines.events.X] = { handler = fn(e), filter = EventFilter│nil } }` — ядро объединяет
  обработчики всех модулей: для одного события вызывает их по очереди под `pcall`; фильтры склеивает
  (массивы конкатенирует; если у кого-то `filter = nil` — регистрирует без фильтра). Для
  `on_entity_damaged` / `on_entity_died` фильтр `{{filter="type", type="character"}}` обязателен.
  Фильтры только «или» (`mode="and"` запрещён — ядро падает с понятной ошибкой); обработчик может
  получить сущность, отфильтрованную для другого модуля, — проверять самому;
- `M.on_nth = { [n] = fn(e) }` — ядро склеивает в один `script.on_nth_tick` на каждое `n`;
- `M.on_init()`, `M.on_configuration_changed(data)` — ядро вызывает у всех.

Модули **не** вызывают `script.on_event`, `script.on_nth_tick` и `commands.add_command` сами.
`require` — только при загрузке файла. Своё состояние модуль хранит только под своим ключом `storage`
(PROTOCOL §7). Доступ к ядру помимо `ctx`: чтение — `jobs.active`, `jobs.queue_len`, `jobs.queue_of`,
`events.query`; рефлекс ставит задачу через `jobs.op_act`. В `storage.jobs` пишет только ядро.

### MCP-сервер `server/factorio_partner/`
Python ≥ 3.11, FastMCP (stdio). Тонкий слой над `core.py`.

| Файл | Что делает |
|---|---|
| `server.py` | инструменты MCP `partner_*` (и служебные `admin_*` при запуске с `--admin`); `PartnerError` → `ToolError` |
| `core.py` | `op_*`: проверка ключа помощника, аргументов, лимитов; курсоры событий и ожидание; защита от зацикливания (`repeated_failure`); загрузка чертежей через `blob_put`. Про MCP ничего не знает |
| `validate.py` | белые списки `do` и полей по ACTIONS.md, границы чисел; неизвестное поле до мода не доходит |
| `bridge.py` | конверт v1, два RCON-соединения (`cmd` — команды агента, `poll` — опрос событий), повтор тем же `id`, распознавание `game_paused` и `game_reloaded` |
| `rcon.py` | RCON на `factorio-rcon-py`; шлёт только `/partner <JSON>` |
| `brief.py` | `partner_brief`: короткие правила честности, заметки профиля forge, стиль общения |
| `forge.py` | связка с factorio-forge: `partner_plan`, заметки профиля для брифа |
| `savenotes.py` | правила хозяина (с подтверждением в игре) и память помощника по сейвам; инструмент `partner_notes` |
| `config.py` | настройки из окружения (`FP_*`, [MCP.md](MCP.md)) |
| `cli.py` | отладочный вход: JSON из stdin → JSON в stdout теми же `op_*`; флаги запуска `--helpers`, `--body` |
| `errors.py` | `PartnerError` — отказ с кодом из PROTOCOL §3 или MCP.md |

### Агентский слой `agents/` и `.claude/agents/partner.md`
- `.claude/agents/partner.md` — тип агента `partner`: белый список инструментов (только `partner_*`),
  правила работы (кто приказывает, честность, цикл поручения, ожидание, разбор отказов, рефлексы,
  жидкость и выходы с участка, разметка добычи, лента до базы, бой, правила хозяина).
- `agents/launch.py` — запуск: спрашивает число помощников и вид тела, выдаёт ключи, готовит тела в
  игре, пишет конфигурацию MCP и первые сообщения агентам.
- `agents/workflows/partner-play.js` — сценарий запуска: по агенту на помощника, смены до слова
  хозяина «отбой».
- `agents/style.md`, `agents/examples/` — стиль общения и разборы типовых поручений;
  `agents/lint.py` — проверка агентского слоя без игры (формат агента, имена инструментов, вызовы в
  примерах).

### Стенд `tools/pc/`
Живые тесты на сервере Factorio без окна, на копии тестового сейва, по SSH на отдельном ПК.
`run-live.ps1` (машина разработчика) собирает пакет, разворачивает сервер через `remote/stand.ps1`,
гоняет сценарий, останавливает сервер и забирает итоги. `live_client.py` — единственная точка отправки
команд в игру (только конверты `/partner`); `server_client.py` гонит сценарий через настоящий пакет
сервера; `pack.py` собирает zip мода и пакет стенда; `scenarios/` — сценарии. Подробнее —
[TESTING.md](TESTING.md), [E2E.md](E2E.md), `tools/pc/README.md`.

`tools/run_lua_tests.py` — раннер юнит-тестов Lua (см. [TESTING.md](TESTING.md)).

## Как идёт команда и событие

**Команда (агент → тело).**
1. Агент вызывает инструмент `partner_*` с `helper` и `key`.
2. `server.py` → `core.py`: проверка ключа (`hmac.compare_digest`), аргументов (`validate.py`), лимитов.
3. `bridge.py` оборачивает вызов в конверт v1 `{"v":1,"id","op","helper","args"}` и шлёт по RCON как
   `/partner <JSON>`. Не пришёл ответ — повтор **тем же `id`**: мод вернёт сохранённый ответ из кольца
   `recent`, ничего не выполнится дважды.
4. Мод (`dispatch.lua`) разбирает конверт, отклоняет вызов из чата игрока, находит операцию.
5. Операция чтения выполняется сразу и отвечает данными (одна строка JSON через `rcon.print`).
   Действие (`act`) проверяется по схеме, получает номер задачи и становится в очередь помощника
   (`jobs.lua`); ответ — `{ok, job}`.
6. Каждый тик активная задача делает шаг (`start/tick/stop` действия) через `ctx`. Предметы берутся
   только из инвентарей и контейнеров, тело только ходит, постройка идёт из своих предметов.

**Событие (тело → агент).**
1. Действие, рефлекс или ядро кладёт событие в буфер `events` (`job_done`, `job_failed`, `died`,
   `respawned`, `player_said`, `attacked`, …). Буфер — кольцо из 500 событий с монотонным номером `seq`,
   переживает загрузку сейва.
2. `partner_wait` на сервере опрашивает буфер по второму соединению (`poll`) от курсора помощника с
   фильтром шума и возвращает события агенту; пока ждёт, `cmd`-соединение свободно для команд.
3. Громкие события (`loud`) будят ожидание сразу; шумные копятся.

**Рефлексы.** Агент не успевает за живой игрой, поэтому быстрые реакции живут в моде: раз в 10 тиков
ядро вызывает `check` каждого включённого рефлекса. Рефлекс может поставить задачу
(`jobs.op_act`), после боя `flee` возвращает помощника к прерванному делу. Набор рефлексов агент меняет
операцией `reflexes`; `death` работает всегда.

## Видимость и честность
- Транспорт — только команды мода по RCON (`/partner`), никогда `/c`, `/sc`, `/silent-command`
  (PROTOCOL §1, §6). Поэтому достижения остаются включёнными.
- Статичное (плитки, руда, призраки) мод читает из открытых чанков; живое (враги, содержимое
  контейнеров и машин) — из видимых чанков или не дальше 32 клеток от тела (`core/vis.lua`).
- Свойства плиток, жидкостей, планет, предметов берутся из прототипов игры (`perception/tiles.lua`,
  `lookup`, `supply`), а не из таблиц в коде (PROTOCOL §6.12).

## Хранилище
Всё состояние мода лежит в `storage` под ключами верхнего уровня (список — PROTOCOL §7: `proto`,
`helpers`, `jobs`, `events`, `recent`, `blobs`, `reservations`, `vision`, `reflexes`, `reflex_state`,
`path_requests`, `mining_last`, `belt_last`). Ядро создаёт все ключи при загрузке и мигрирует схему
(`migrate.lua`); модуль пишет только под своим ключом. На стороне сервера данные лежат в `FP_HOME`
(вне репозитория): `helpers.json` с ключами, `logs/`, `launch/`; правила и память по сейвам — в
`save-notes/` папки проекта.
