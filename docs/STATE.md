# Что видит агент (операции чтения)

Ответы — компактный JSON, координаты округлены до 0.1, качество только `normal`.
Два уровня обзора (PROTOCOL §6.7): **статичное** — в открытых (`is_chunk_charted`) чанках,
**живое** (враги, содержимое контейнеров/машин, предметы на земле) — только в видимых
(`is_chunk_visible` или ≤ 32 клеток от живого тела помощника). Каждая операция — `M.ops.<op>` в
`scripts/perception/<файл>.lua`, `ctx = {helper_id?, entity?}`; регистрация — одной строкой в
`control.lua`. Центр по умолчанию — **помощник**; `near:"player"` — хозяин (`physical_position`,
иначе `no_player`); `center` и `near` вместе → `bad_args`. Без помощника («h?») поверхность, сила и
центр — хозяина (PROTOCOL §4). Ответы операций только для чтения длиннее 16 КБ не попадают в память
повторов `storage.recent` (PROTOCOL §2). Ответ инструмента агенту больше 24 КБ сервер отклоняет
(`response too large`) с подсказкой, каким аргументом сузить (MCP.md).

## `state` (h)
```json
{"helper":"h1","surface":"vulcanus","pos":{"x":52.4,"y":93.4},"health":250,"max_health":250,
 "reach":{"build":10,"reach":10,"resource":2.7,"pickup":1},
 "inv":{"iron-plate":40,"coal":12},"inv_free":72,"armor":"power-armor-mk2",
 "robots":{"construction":10,"available":9},
 "job":{"job":57,"do":"walk","progress":[12,40]},"queue":2,"idle_ticks":0,"busy_share":0.82,"busy_window":36000,
 "players":[{"name":"Owner","owner":true,"online":true,"surface":"vulcanus","pos":{"x":48,"y":90},"dist":4.2}],
 "near":{"enemies":[],"containers":3},"vision":true,"body":"character","module_errors":0,"tick":4109766,"seq":812}
```
- `inv` — главный инвентарь (`normal`), `inv_free` — пустых ячеек; `armor` — имя брони, если есть;
  `robots` — дроны логистической ячейки тела (всего / свободных).
- `job` берётся из `jobs.active(helper)` ядра (ACTIONS.md), `progress` — `[сделано, всего]`;
  `queue` — ждущих задач без активной.
- `idle_ticks` — сколько тиков подряд у помощника нет активной задачи (0, пока она есть; шаг учёта
  30 тиков). `busy_share` — доля времени с активной задачей за последние 10 минут игрового времени
  (0…1, два знака; поля нет, пока учёт не накопил данных), `busy_window` — сколько тиков вошло в эту
  оценку (до 36000). Учёт — `scripts/core/metrics.lua`, по `jobs.active`; очередь не меняет.
- `players` — все игроки сейва; `surface`/`pos` — только у онлайн-игроков с телом, `dist` — если они
  на поверхности помощника.
- `near.enemies` — только в видимых чанках, радиус 32 клетки, до 20 ближайших `{name, pos, dist}`;
  враги — сила `enemy`, типы `unit`, `unit-spawner`, `turret`, `spider-unit`, `segmented-unit`.
  `near.containers` — сколько своих сундуков (`container`, `logistic-container`) в радиусе 32 в
  открытых чанках.
- `vision` — включён ли обзор помощника (`vision` ниже).
- `body` — вид тела, `"character"│"player"` (PROTOCOL §7 «Два вида тела»).
- `module_errors` — число: тот же счётчик падений модулей и рефлексов, что в `hello` (агент видит
  его рост в течение игры). Если мод их не прислал, сервер добирает `module_errors` через `hello`, а
  `body` — через `helper_list`.

## `map` (h?, `center?│near?:"player"`, `radius?=16` (≤ 32), `types?`, `names?`)
```json
{"bbox":{"x0":44,"y0":85,"x1":60,"y1":101},
 "axis":"x: 44...|50.......|60",
 "rows":["...ccc....D......", "..."],
 "legend":{".":"земля","~":"не пройти: lava","#":"утёс/скала","?":"не открыто","@":"помощник","P":"игрок",
           "D":"бур","F":"печь","A":"сборщик","B":"лента","I":"манипулятор","C":"сундук","E":"столб",
           "g":"призрак","c":"руда: calcite","w":"руда: tungsten-ore","k":"руда: coal"},
 "entities":[{"c":"D","name":"electric-mining-drill","pos":{"x":55.5,"y":90.5},"dir":0}],
 "truncated":false}
```
- Строки сверху вниз (север → юг), слева направо. `bbox` — координаты крайних клеток,
  `axis` — подпись столбцов (метка каждые 5 клеток), чтобы не считать символы.
- `map` **никогда** не отдаёт `not_charted`: неоткрытое рисуется `?`.
- Руды — свои строчные буквы, назначаются по первой свободной букве имени; легенда в ответе
  всегда полная для того, что нарисовано. Сущности — `bounding_box` закрашивается на всю площадь.
- В ответе ещё `surface`. Постоянные символы легенды сверх примера: `H` другой помощник,
  `L` труба, `T` дерево, `X` враг, `O` другая своя постройка.
- `entities` — до 100; по умолчанию только свои постройки (без лент, труб и столбов — их много),
  призраки и видимые враги; нейтральное (деревья, камни, руда) — только при явном `types?`/`names?`
  (≤ 32 имён каждый). Поля: `c, name, pos, dir, unit` (unit_number), у призрака `ghost:true` и
  `name` = имя внутренней сущности. `dir` — `defines.direction` 2.0: **16 направлений**, север 0,
  восток 4, юг 8, запад 12. Враги — только в видимых чанках.
- **Жидкости и преграды (все планеты, правила — из игры, PROTOCOL §6.12).** `~` — плитка, по которой
  персонаж **не может пройти** (маска столкновений плитки пересекается с маской персонажа: глубокая
  вода, лава, мазутный и аммиачный океан и т.п.); `,` — пройти можно, но строить без подложки нельзя
  (у плитки есть `default_cover_tile`, а персонаж проходит). Подпись в легенде называет плитки,
  которые реально нарисованы: `"~":"не пройти: lava"`, `",":"мелко: oil-ocean-shallow"` — до 6 имён и
  `+N`. Отдельное поле `liquids:{[tile_name]={n, cover?, cover_ok}}` (≤ 16 имён) — сколько клеток, чем
  накрывается (`cover` — имя предмета подложки, есть только когда у плитки есть `default_cover_tile`)
  и доступна ли подложка сейчас (`cover_ok`, есть всегда).
- Как считать (2.0): тайлы — одним `surface.find_tiles_filtered{area}`, проходимость — по
  `tile.prototype.collision_mask` и маске прототипа `character`; `#` — `cliff` и
  `simple-entity` с `prototype.count_as_rock_for_filtered_deconstruction`; `?` — по
  `force.is_chunk_charted(surface, chunk)`; сущности — `find_entities_filtered{area,
  force={own, "neutral", "enemy"}}`.

## `resources` (h?, `center?│near?`, `radius?=64` (≤ 128), `name?`)
```json
{"patches":[{"name":"calcite","center":{"x":120,"y":40},"area":{"left_top":{"x":100,"y":28},"right_bottom":{"x":141,"y":55}},
  "tiles":612,"amount":3400000,"dist":70.2}],"truncated":false}
```
Пятна — кластеризация ресурсов по имени и соседству (8-связность), только открытые чанки,
не больше 20 пятен (ближайшие). `dist` — до центра пятна; пятна обрезаются кругом поиска: у такого
пятна `clipped:true`, а `tiles` и `amount` — только видимая в круге часть (нижняя оценка).
Без `name` мелкие источники (гейзеры и т.п.) могут занять все 20 мест — искать руду с `name`.
Неизвестное или не-ресурсное `name` → `bad_args`. Радиус 128 — дорогой режим (256×256 клеток,
десятки тысяч сущностей): агенту начинать с 32–64.

## `stock` (h?, `center?│near?`, `radius?=64 (≤128)`, `items?`, `limit?=50 (≤200)`)
```json
{"containers":[{"unit":123,"name":"steel-chest","pos":{"x":10.5,"y":4.5},"dist":12.0,"items":{"iron-plate":800}}],
 "total":{"iron-plate":800},"hidden":2,"truncated":false}
```
`items` — фильтр: массив имён (≤ 100); форму `{name:count}` мод тоже принимает, но берёт из неё только
имена. Через сервер (`partner_stock`) — только массив имён.
Склады = контейнеры и логистические сундуки своей силы. Содержимое — только в видимых
чанках; невидимые считаются в `hidden`. Машины не считаются. Пустые (или без нужных `items`)
сундуки в `containers` не попадают; `truncated` — про список, `total` и `hidden` — по всем сундукам.

## `ghosts` (h?, `area?│radius?=64` (≤ 128), `center?│near?`)
```json
{"count":24,"by_name":{"electric-mining-drill":16,"transport-belt":120},
 "need":{"electric-mining-drill":16,"transport-belt":120},
 "have":{"helper":{"transport-belt":40},"stock":{"electric-mining-drill":30,"transport-belt":500}},
 "missing":{},"blocked":[{"name":"transport-belt","pos":{"x":3.5,"y":7.5}}],"area":{...}}
```
`area` и `radius` вместе → `bad_args`; сторона `area` ≤ 128.
`blocked` — призраки, у которых `ghost_revive`-проверка = false (PROTOCOL §6.5), список до 50;
`blocked_total` — сколько всего. При > 1000 призраков проверяются не все: `blocked_partial:true`,
`blocked_total` — нижняя оценка. `need` включает `item_requests` призрака (модули) и предметы для
призраков плиток (`tile-ghost`); `tiles:int` — сколько призраков плиток, в `count`/`by_name` они не
входят. `have.stock` — по складам в радиусе 64 от центра (видимые).

## `rates` (h?, `scope?`, `area?`, `surface?`, `period?`, `items?` (≤ 100), `top?=20`)
`top` — до 200 в моде, до 100 через сервер (`partner_rates`).
- `scope:"surface"` (по умолчанию поверхность помощника; в 2.0 статистика только по поверхности):
  `stats = force.get_item_production_statistics(surface)` (и `get_fluid_production_statistics`);
  made = `stats.get_flow_count{name, category="input", precision_index=<период>, count=true}`,
  used — то же с `"output"` (в API 2.0 `input` — произведено, левая колонка окна статистики;
  `output` — потреблено); имена — из `stats.input_counts`/`output_counts`.
  `period`: `1m` → `defines.flow_precision_index.one_minute`, `10m` → `ten_minutes`,
  `1h` → `one_hour`. Значения — **сумма за период** (не в минуту). Вернуть `top` по обороту
  (общий для предметов и жидкостей) или только `items`.
```json
{"scope":"surface","surface":"vulcanus","period":"1m",
 "items":{"iron-plate":{"made":1200,"used":950}},"fluids":{"water":{"made":36000,"used":35000}},"truncated":true}
```
- `scope:"area"` (нужна `area`, сторона ≤ 128) — **номинальная** оценка по машинам в `area`
  (`nominal:true`, машина может простаивать), **в минуту**:
  - циклов/мин = `crafting_speed / recipe.energy × 60` (`crafting_speed` в 2.0 уже с модулями и
    маяками); `in` = ингредиенты × циклы (**без** продуктивности); `out` = Σ (ожидаемое количество с
    `probability`, `amount_min/max`, `extra_count_fraction` + часть сверх `ignored_by_productivity`
    × `productivity_bonus`) × циклы; бонус ограничен `maximum_productivity` рецепта (по умолчанию 3,
    т.е. +300 %);
  - буры: `mining_speed × (1 + speed_bonus) / mining_time × 60` по `mining_target`; жидкость
    `required_fluid` — `fluid_amount / 10` на цикл; бесконечные ресурсы × `amount / normal_resource_amount`;
  - печь без текущего рецепта — по `previous_recipe`;
  - машины: `assembling-machine`, `furnace`, `rocket-silo`, `mining-drill`.

  Ответ: `{"scope","surface","area","per":"1m","machines":[{"name","recipe","count","in":{...},"out":{...}}],
  "net":{...},"nominal":true,"hidden":N,"idle":N,"truncated":bool}` — `hidden` машины в невидимых
  чанках (живые данные — только видимые), `idle` — без рецепта/цели или не-`normal` качества,
  `machines` до 100 групп.
- Без помощника поверхность/сила — хозяина (хозяин офлайн и нет `surface` → `no_player`); явный
  `surface` сильнее. Ошибки: `bad_args`, `limit`, `not_found` (нет поверхности), `no_player`,
  `internal` (сбой `get_flow_count` — не пустой ответ).

## `find` (h?, `item`, `kinds?`, `surface?`, `limit?=20 (≤50)`) — поиск по всей базе
«Где у нас делают/тратят/хранят X» по всей поверхности, а не в области. Сделано по образцу мода
Factory Search (MIT): обычный `find_entities_filtered` и разбор рецептов. Программного входа с
данными у того мода нет (`remote` только открывает окно игроку), поэтому поиск свой.
- `item` — имя предмета или жидкости; `kinds` — подмножество `["producers","consumers","storage",
  "entities"]` (по умолчанию первые три).
- Кто есть кто: `producers` — машины с рецептом, дающим `item`, и буры, чья руда его даёт
  (производитель жидкости ищется по текущему рецепту или жидкости; пустой насос без жидкости не
  находится); `consumers` — машины с рецептом, где `item` — ингредиент; `storage` — сундуки и
  цистерны, где он лежит; `entities` — постройки с именем `item` (годится и имя постройки, не только
  предмета).
- Только сущности силы помощника в открытых чанках; `storage` — только видимое (PROTOCOL §6.7),
  остальное `storage` считается как `hidden:int`.
- Ответ — **группы** (постройки ближе 32 клеток друг к другу — одна группа), ближайшие к помощнику
  (или хозяину) первыми: `{item, groups:[{kind, pos, dist, count, names:{[name]=n}, recipe?, amount?}],
  total:{producers,consumers,storage,entities}, surface, truncated?, hidden?}`; в группе — до 8 самых
  частых имён, остальные — `names_more:int`. `total` — только по запрошенным `kinds`. `pos` — центр
  группы: годится как `center` для `map`/`rates`/`ghosts`/`collect`; как цель `walk` — только с
  `radius` ≥ 3 (центр может оказаться внутри постройки). Группировка приближённая (сетка, соседние
  постройки на 32–45 клеток могут попасть в одну группу).
- Лимит — по работе, а не по размеру карты: найдено больше 20000 сущностей → `limit` (сузить `kinds`).
  Числа чанков поверхности лимит не касается: открытость проверяется у найденных сущностей.

## `status` (h?, `radius?=64` (≤ 128), `limit?=20` (≤ 50), `center?│near?`) — что стоит и почему
Машины силы хозяина в радиусе, которые не работают, и причина по статусу движка. Берётся из индекса
построек (`scripts/core/index.lua`), а не сканом силы: постройки ведутся по событиям (построено,
снесено, умерло, склонировано), сейв без индекса заполняется раскруткой по тикам (не больше 4 открытых
чанков и 400 построек за тик; сам список открытых чанков поверхности тоже собирается порциями). Силу и
позицию записи индекс сверяет с сущностью при выдаче: сменила силу — запись снимается, переместилась —
переезжает в свой чанк. В индексе — только сущности силы хозяина типов: сборщики, печи, буры,
ракетная шахта, лаборатории, котлы, генераторы, реакторы, фермерские башни; манипуляторы и прочее с
горелкой — тоже, но как «горелка», не как машина.
```json
{"surface":"nauvis","center":{"x":2,"y":0},"radius":64,
 "machines":{"seen":11,"running":2,"stopped":8,"hidden":0,"ignored":1},
 "causes":{"power":3,"fuel":1,"output":1},
 "stopped":[{"name":"assembling-machine-1","reason":"no_power","cause":"power","recipe":"iron-gear-wheel",
             "count":2,"pos":{"x":14,"y":0},"dist":12}],
 "index_ready":true,"helper":{"job":{"job":7,"do":"wait"},"queue":0}}
```
- `machines`: `seen` — машины с прочитанным статусом, `running` — `working` и `normal`, `stopped` — остановившиеся
  (без «мягких» разрядов ниже), `hidden` — в невидимых чанках (статус — живое, PROTOCOL §6.7: видимый чанк или ≤ 32
  клеток от тела), `ignored` — помеченные на разбор, `unknown` — у сущности нет статуса (поле есть,
  только если больше нуля), `slow` — машины в `low_power` (работают, но медленно), `waiting` — лаборатории
  без исследования и этапы пуска ракетной шахты (оба поля — только если больше нуля).
- `stopped` — группы «имя + статус + рецепт»: `reason` — имя статуса из `defines.entity_status` как
  есть, `cause` — разряд: `power` (`no_power`, `not_plugged_in_electric_network`), `fuel`
  (`no_fuel`), `resource` (`no_minable_resources`), `input` (нет сырья, жидкости, пакетов науки),
  `output` (`full_output`, `waiting_for_space_in_destination`), `recipe` (`no_recipe`), `heat`
  (`low_temperature`), `disabled`, `other` (незнакомый статус — имя остаётся в `reason`). Мягкие разряды — не остановка, идут
  после остальных: `slow` (`low_power`), `research` (`no_research_in_progress`), `rocket`
  (`preparing_rocket_for_launch`, `waiting_to_launch_rocket`, `launching_rocket`). Порядок:
  разряд в этом порядке, потом больше машин, потом ближе. `pos`/`dist` — ближайшая машина группы,
  `recipe` — рецепт, если он есть. `causes` — число машин в строках по разрядам (мягкие тоже).
  `truncated:true`, если групп больше `limit`.
- `index_ready:false` — раскрутка индекса ещё идёт, ответ может быть неполным.
- `helper:{job?, queue}` — задача помощника (без `h` поля нет).
- Центр — помощник, `center` или хозяин (`near:"player"`); без помощника поверхность и сила — хозяина.
  Имён прототипов в коде нет: статусы, рецепты и имена построек читаются у самих сущностей.
  Ошибки: `bad_args` (в том числе `radius` > 128 или `limit` > 50 — сервер проверяет их до мода; сам мод
  на такой запрос в обход сервера отвечает `limit`), `no_player`.

## `access` (h?, `area` │ `center?│near?` + `radius?=32 (≤64)`) — суша и выходы с участка
Отвечает на вопрос «можно ли сюда дойти и подвести ленту, и с какой стороны». Нужна там, где
участок окружён жидкостью или утёсами (лавовые озёра, острова), особенно пока нет фундамента и
отсыпки. Участок — `area` (сторона ≤ 128) либо квадрат `radius` вокруг центра; `area` вместе с
`radius`/`center`/`near` → `bad_args`.
```json
{"area":{...},"surface":"vulcanus","land":812,"liquid":460,"liquids":{"lava":460},"enclosed":false,
 "exits":[{"side":"south","pos":{"x":118,"y":70},"width":14,"neck":"wide"},
          {"side":"west","pos":{"x":96,"y":41},"width":3,"neck":"narrow"}],
 "best":"south","reachable":true,"warnings":["narrow_access:west"]}
```
- Рамка — `area`, расширенная на 8 клеток. `land` / `liquid` — клеток суши и непроходимого внутри
  `area`; `liquids` — какие плитки (≤ 12 самых частых).
- `exits` — участки рамки, где суша, связанная с сушей `area`, выходит наружу: сторона, середина,
  ширина по рамке и `neck` — самое узкое место по дороге от участка до этого выхода:
  `"narrow"` (1–2 клетки), `"medium"` (3–4), `"wide"` (≥ 5). `width` и `neck` независимы. Считается
  заливкой проходимых клеток с «усадкой» маски на 1 и 2 клетки (утёсы, камни и постройки — преграды,
  деревья — нет). До 8 выходов; порядок — по `neck` (wide → medium → narrow), потом по ширине на
  рамке, потом north, east, south, west. У одной стороны может быть несколько выходов. `best` —
  сторона первого выхода.
- `enclosed:true` — выходов нет (остров): пешком не дойти, ленту не вывести.
- `reachable` — есть ли путь от помощника (или хозяина) до суши участка по той же заливке в пределах
  рамки; помощник вне рамки → поле опущено (ответ даёт `walk`/`approach`).
- `warnings`: `enclosed`; `narrow_access` без стороны — лучший выход узкий (значит, узкие все);
  иначе `narrow_access:<сторона>` — по одному на каждую сторону с узким выходом; `not_charted:N` —
  столько клеток рамки не открыто (они считаются преградой).
- Только открытые чанки: участок не открыт совсем → `not_charted`. Расчёт вынесен в функцию (`scripts/perception/access.lua`), которую зовёт
  и `plan_mining` для своих предупреждений.

## `recipes` (h, `filter?`)
Перебор `force.recipes`: `enabled`, не `hidden`, категория ∈
`prototypes.entity["character"].crafting_categories`; значение —
`entity.get_craftable_count(name)`, нули не выводить; `filter` — подстрока имени (`""` — без фильтра).
`{"craftable":{"iron-gear-wheel":20,"pipe":40}}`.

## `vision` (h, `on`) — обзор помощника
Раз в 60 тиков для каждого живого помощника с `on`: чанки в радиусе 2 чанков от тела, которые
сгенерированы (`surface.is_chunk_generated`) и либо не открыты, либо открывались ≥ 10 с назад
(`storage.vision.charted[key]`); не больше 8 чанков за итерацию на помощника, ближние первыми;
`force.chart(surface, area)` по границам чанков. Хранение: `storage.vision = {on={[helper]=
{on, unit}}, charted={["<surface_index>:<cx>:<cy>"]=tick}}`. Нет записи — значит `on=true`
(ядро при `helper_spawn` ничего не пишет); запись с другим `unit_number` (новое тело после spawn
или возрождения) считается устаревшей → обзор снова включён. Мёртвый или удалённый помощник
(`storage.helpers[id].state ~= "alive"`) обзор не ведёт; телу-игроку карту открывает сам движок.

## `supply` (h, `item`, `count?=1` (1..10000), `depth?=3` (1..5)) — что из чего и где это взять
Хозяин даёт цель в общих словах («поставь ещё литейных»), а помощник должен сам развернуть её
до сырья и найти источники, не спрашивая, где что стоит. Один вопрос — один ответ: дерево нужного с
источниками по каждому узлу. Всё из игры (рецепты и категории — из прототипов и `force.recipes`), без
имён предметов, машин и планет в коде (PROTOCOL §6.12). Модуль — `scripts/perception/supply.lua`.

Ответ: `{item, count, surface, tree: node, summary:{short:[{name, n}], raw:[{name, n}]}, nodes:int,
truncated?:true, hidden?:int, warnings:[...]}`.

`node` = `{name, kind:"item"│"fluid", need:int, have:int, short:int, stored?, producers?, recipe?,
resource?, note?}`:
- `have` — сколько в карманах помощника **ещё не занято** узлами, стоящими раньше в обходе в
  ширину (один и тот же предмет в двух ветках карманы не считает дважды); `short = max(0, need − have)`.
- `stored` — где это лежит на базе: `{total:int, pos, dist, n:int}` — всего в видимых сундуках и
  ближайшая группа (`n` — количество предмета в ней, а не число сундуков; группы — как `storage` у
  `find`; невидимое — в общий `hidden`).
- `producers` — машины базы, у которых **сейчас стоит рецепт**, где этот предмет среди продуктов
  (включая побочные): `{count, pos, dist, names:{[имя]=n}, recipe, out:int}` — ближайшая группа и
  сколько готового лежит в выходах её машин (`out`; его можно забрать `extract`). Буры здесь не
  считаются — они в `resource.drills`.
- `recipe` — как это делается, если узел раскрыт: `{name, hand:bool, category, yield:int,
  crafts:int, time:number, makers?, ingredients:[node…]}`.
  - Выбор рецепта: открытый у силы (`enabled`), не скрытый, с чистой прибавкой предмета, где предмет —
    основной продукт; из нескольких — тот, что уже стоит в машинах базы, иначе доступный руками, иначе
    с меньшим числом ингредиентов; при равенстве — рецепт с именем предмета, потом по алфавиту.
    Предмет есть только как побочный продукт (несколько продуктов без `main_product`) → `no_recipe`.
  - `hand` — может ли персонаж сделать это руками (категория рецепта входит в категории крафта
    персонажа и среди ингредиентов нет жидкостей).
  - `makers` — машины базы, **способные** делать этот рецепт по категории (даже если сейчас стоит
    другой): `{count, pos, dist, names}`; нет ни одной — поля нет.
  - `crafts = ceil(short / yield)`; `need` у ингредиента = его количество в рецепте × `crafts`;
    `time` — секунды на все крафты (`energy × crafts`) при скорости 1.
- `resource` — если предмет добывается из земли: `{name (имя ресурса), pos, dist, amount, drills:int}`
  — ближайшее пятно в открытых чанках не дальше 128 клеток от помощника (как `resources`) и сколько
  буров на нём уже стоит. Дальше или клеток ресурса вокруг слишком много для поиска — поля нет, узел
  остаётся в `summary.raw`.
- `note` — почему узел не раскрыт: `"enough"` (`short = 0`), `"depth"`, `"no_recipe"` (сырьё без
  рецепта), `"not_researched"` (рецепт есть, но не открыт), `"cycle"`.

Правила:
- Узел раскрывается (поле `recipe` с ингредиентами), только если `short > 0` и глубина не исчерпана.
  Источники (`stored`, `producers`, `resource`) указываются у каждого узла, раскрыт он или нет.
- `summary.short` — плоский список всего, чего не хватает в карманах, по всему дереву (узлы
  `note:"cycle"` не входят); `summary.raw` — то из него, что добывается из земли или не имеет рецепта.
- Размер: не больше 60 узлов. Обрезка видна только как `truncated:true` у ответа (узлы ниже —
  `depth`): нужный узел дозапросить отдельным `supply`. Работа: база просматривается **одним**
  проходом по сущностям силы помощника в открытых чанках (а не поиском на каждый узел); больше 20000
  сущностей → `limit`. Группы и расстояния — как у `find`.
- Видимость — PROTOCOL §6.7: содержимое сундуков и выходов машин только в чанках с текущим обзором,
  остальное считается в `hidden`. Чужая сила не просматривается.
- `item` неизвестен игре → `not_found`. `warnings` (≤ 20): `not_researched:<имя>` (неоткрытому
  рецепту — только это), `no_source:<имя>` (только у узла с `no_recipe`: нет ни запаса, ни машины, ни
  пятна), `other_surface` (ничего нужного на этой поверхности нет).
- Ответ сервера больше 24 КБ → `response too large` с подсказкой уменьшить `depth`.

## `lookup` (h?, `name`, `kind?`, `limit?=20` (1..50)) — справка «как в Факториопедии»
Помощник не знает игру наизусть, а моды добавляют своё. Факториопедия — окно для игрока, мод
прочитать его не может, но она показывает данные самой игры — их мод читает напрямую. «Что это вообще
такое в игре», в отличие от `supply` («как это получить на моей базе»). Всё из прототипов и сил игры,
без имён в коде (PROTOCOL §6.12). Модуль — `scripts/perception/lookup.lua`. Только чтение: ничего не
изучает, не меняет, карту не открывает. Сила — помощника (без помощника — хозяина).

`kind` — `"item"│"fluid"│"recipe"│"technology"│"entity"`; без него — первое совпадение по имени в таком
порядке. `limit` больше 50 → `limit`. Имя неизвестно (в том числе технология из выключенного мода) →
`not_found`; до 5 имён прототипов, содержащих эту строку (без учёта регистра), идут в тексте ошибки
после «; suggest: » (ошибка по PROTOCOL §2 несёт только `{code, text}`); сервер выносит их в
`detail.suggest`.

**Предмет или жидкость** → `{kind, name, type, stack_size?, place_result?, fuel_value?,
made_by:[recipe…], made_by_total, used_in:[{recipe, enabled, category}], used_in_total,
mined_from:[{resource, required_fluid?, amount?}], researched_any:bool}`:
- `recipe` = `{name, enabled, hidden?, category, hand:bool, time, ingredients:[{name, type, amount}],
  products:[{name, type, amount, probability?}], machines:[имя…] (≤ 10, все не скрытые прототипы машин
  игры, чьи crafting_categories содержат категорию), machines_total, unlocked_by?:[имя технологии…]
  (≤ 5, только если рецепт не открыт)}`; `hand` — как у `supply`.
- `made_by` — рецепты, где это среди продуктов (основной продукт — первыми); `used_in` — где это
  ингредиент; скрытые рецепты в обоих списках не показываются; оба списка ≤ `limit`, полное число — в
  `*_total`.
- `mined_from` — ресурсы (и деревья, камни), при добыче которых это выпадает.
- `researched_any` — открыт ли хоть один рецепт из `made_by` (или предмет добывается).

**Рецепт** → тот же `recipe`, плюс `unlocked_by` всегда (пусто — открыт с начала).

**Технология** → `{kind:"technology", name, researched, enabled, available:bool (все предпосылки
изучены), prerequisites:[{name, researched}], missing:[имя…] (неизученные технологии, без которых эту не
изучить, в порядке изучения, ≤ 30), unlocks:[рецепт…], other_effects:[{type, …}], cost?:{count,
ingredients:[{name, amount}], time}, trigger?:{type, …} (технологии, изучаемые действием, а не колбами)}`.
У технологии с бесконечными уровнями `cost` — текущего уровня.

**Постройка (entity)** → `{kind:"entity", name, type, size:{w,h}, items_to_place:[имя…],
crafting_categories?, crafting_speed?, mining_categories?, energy_usage?, mineable_results?}` — только
поля, которые у прототипа есть.

Размер ответа: списки ≤ `limit`, в целом ≤ 24 КБ на сервере (больше — `response too large` с подсказкой
уменьшить `limit`).
