# Протокол мод ↔ сервер (v1)

Главный контракт проекта. Мод `factorio-partner` (Lua, Factorio 2.0.77, Space Age) и
MCP-сервер `factorio_partner` (Python) общаются **только** так, как описано здесь.
Связанные документы: [ACTIONS.md](ACTIONS.md) (действия), [EVENTS.md](EVENTS.md) (события и
рефлексы), [STATE.md](STATE.md) (операции чтения), [MCP.md](MCP.md) (инструменты агента),
[TESTING.md](TESTING.md), [ARCHITECTURE.md](ARCHITECTURE.md) (устройство мода и сервера).

## 1. Транспорт
- RCON на `127.0.0.1` (хост мультиплеера из меню: `local-rcon-socket` /
  `local-rcon-password`; выделенный сервер: `--rcon-bind` / `--rcon-password`).
- Каждый вызов — **команда мода** `/partner <JSON>`. Никогда `/c`, `/sc`,
  `/silent-command`: они навсегда отключают достижения. Команды мода по RCON достижения
  не трогают ([ENGINE-NOTES.md](ENGINE-NOTES.md)).
- Ответ — ровно одна строка JSON через `rcon.print`. Больше мод в RCON ничего не печатает.
- `/partner` из чата игрока (`cmd.player_index ~= nil`) отклоняется: игроку в чат
  `[partner] только для RCON`, в RCON — ничего.
- JSON: `helpers.json_to_table` (вернул не таблицу → `bad_request`) и `helpers.table_to_json`.
  Правила сериализации ответа:
  - в `data`/`detail` только числа, строки, bool и таблицы из них — **никаких LuaEntity/LuaObject**
    (вместо них `unit_number`, `name`, `pos`);
  - без таблиц со смешанными ключами;
  - пустая таблица уходит как `{}`, сервер считает `{}` и `[]` одинаковыми;
  - `null` в JSON мода не бывает (таблица Lua его не хранит): отсутствующее поле — нет ключа;
  - координаты округляются до 0.1.

## 2. Конверт
Запрос:
```json
{"v": 1, "id": "r-000123", "op": "act", "helper": "h1", "args": {"do": "walk", "args": {"to": {"x": 10, "y": -4}}}}
```
- `v` — версия протокола (`1`); не число → `bad_request`, иное число → `version_mismatch`.
- `id` — 1–40 символов `[A-Za-z0-9_.:-]`, уникален **и между перезапусками сервера** (кольцо
  `recent` лежит в сейве): сервер делает `s` + 8 случайных hex на процесс + `-` + счётчик из 6 цифр.
- `op` — из §4 (строка ≤ 40 символов). `helper` — `^[a-z0-9_-]{1,16}$`; обязателен для операций «h».
- `args` — объект по схеме операции (нет `args` — то же, что `{}`).
- Других полей в конверте нет, кроме `owner_ok`: лишнее поле (например, ключ помощника) → `bad_request`.
  Ключ помощника живёт только на сервере (MCP.md) и в мод не уходит.
- `owner_ok` (необязательное: список ключей разрешений, например `["take_lines"]`; пишутся как в `settings`,
  через дефис или с `perm-`; не список или неизвестный ключ → `bad_request`) — разрешение хозяина на
  действия, которые настройки мода разрешают только «спросить» (§4 «Настройки», `settings`). Снимает
  «спросить» только с этих ключей. Ставит **только сервер** и только когда хозяин в чате ответил «да» на
  вопрос о том же поручении и об этих разрешениях; агенту поле недоступно (сервер отказывает `bad_args`).
  Действует на `act`, `plan` (все шаги) и `reflexes` того же запроса. «Нельзя» оно не отменяет.
  Проверяются только запросы по RCON: свои вызовы мода (рефлексы, слово хозяина, возврат после отступления)
  идут мимо этой проверки.

Ответ:
```json
{"v": 1, "id": "r-000123", "ok": true, "tick": 4109766, "seq": 812, "data": {"job": 57}}
{"v": 1, "id": "r-000124", "ok": false, "tick": 4109767, "seq": 812, "error": {"code": "not_reachable", "text": "..."}}
```
- `tick` — `game.tick`, `seq` — номер последнего события в буфере.
- Ошибка несёт только `{code, text}`; текст — без путей к файлам и номеров строк, ≤ 300 байт,
  UTF-8 не режется посреди символа.
- **Идемпотентность:** мод хранит `storage.recent` — кольцо последних 128 ответов по `id`.
  Повторный запрос с тем же `id` возвращает сохранённый ответ и **не** исполняет операцию.
  Поэтому сервер после обрыва соединения может безопасно повторить любой запрос с тем же `id`.
  Исключения (чтобы не раздувать сейв): ответы **операций только для чтения** (`hello`,
  `helper_list`, `jobs`, `events`, `state`, `map`, `resources`, `stock`, `ghosts`, `recipes`,
  `rates`, `find`, `access`, `status`, `supply`, `lookup`, `settings`) длиннее 16 КБ не сохраняются — повтор исполнится
  заново (безопасно, `tick` новый); ответ `limit` на запрос > 8 КБ тоже не сохраняется (операция не
  исполнялась). Ответы операций с последствиями (`act`, `cancel`, `helper_*`, `reflexes`, `vision`,
  `say`, `blob_put`, `owner_hold`) сохраняются всегда.
- Ответ ≤ 200 000 байт (RCON 2.0.77 отдаёт и 300 КБ целиком); больше → `too_large`. Операции,
  которые могут вырасти, ограничены аргументами (радиус, `limit`, `top`).
- Размер **запроса** (параметр команды) ≤ 8 КБ, больше → `limit`. Запрос до 512 КБ мод всё же
  разбирает, чтобы вернуть ошибку с его `id`. RCON сам пропускает и 1 МБ, так что 8 КБ — выбор
  протокола: большое (чертежи) — только частями через `blob_put` (§4).

## 3. Коды ошибок мода
| code | когда |
|---|---|
| `bad_request` | не JSON, нет `v`/`id`/`op`, неверные типы конверта, лишнее поле конверта, нет `helper` у операции «h» |
| `version_mismatch` | `v` ≠ версии мода |
| `unknown_op` | нет такой операции |
| `bad_args` | аргументы не прошли схему (текст называет поле) |
| `no_helper` | помощника нет, либо он мёртв или в `away` (`state ~= "alive"`) |
| `helper_exists` | `helper_spawn`/`helper_attach` при живом теле с этим id или при id, привязанном к телу-игроку |
| `cooldown` | `helper_spawn` раньше, чем через 10 с после `helper_remove`/смерти **любого** тела-персонажа (общая для всех id) |
| `no_player` | нужен игрок онлайн с телом (`player.character`), а его нет / он на другой поверхности |
| `limit` | превышен лимит: помощников, очереди, размера запроса/blob, **верхняя граница** числового аргумента (радиус, `limit`, `top`, сторона `area`, число имён). Нижняя граница, неверный тип, лишнее поле → `bad_args` |
| `not_found` | цель не найдена или не своей/нейтральной силы |
| `not_reachable` | цель на другой поверхности (ходить между поверхностями нельзя) |
| `no_items` | не хватает предметов |
| `cannot_place` | постановка невозможна (`can_place_entity` = false); у чертежа и разметки — ни один призрак не встал; нет места для нового тела |
| `not_charted` | цель или область в неоткрытых чанках |
| `not_visible` | живые данные (враги, содержимое) запрошены вне видимых чанков |
| `reserved` | предметы/область заняты другим помощником |
| `path_failed` | поиск пути не нашёл маршрут |
| `stuck` | застрял, не смог выбраться, или задача без прогресса 60 с |
| `no_space` | в инвентаре помощника нет места (задача не может продолжать) |
| `cancelled` | задача отменена |
| `owner_hold` | `act` не принят: хозяин сказал «стоп» или «иди сюда», hold стоит (EVENTS.md «Слово хозяина») |
| `owner_forbids` | настройка мода запрещает это («нельзя»); `data:{perm}`, текст «запрещено в настройках мода: <подпись>». Не снимается ничем, даже `owner_ok`. Тот же код — агент убирает или меняет охрану хозяина (`evacuate` кнопкой «Охранять здесь»): `data:{owner_guard:true}`, текст «охрану поставил хозяин — снять может только он» |
| `needs_owner_ok` | настройка мода требует разрешения хозяина («спросить»), а этого ключа нет в `owner_ok` конверта; `data:{perm}`, текст «нужно разрешение хозяина: <подпись>» |
| `too_far` | цель дальше предела от тела: рефлекс `evacuate` включается или меняет область, только если центр области не дальше 150 клеток от тела (EVENTS.md «`evacuate`»); `data:{distance, max}` |
| `too_large` | ответ больше лимита |
| `internal` | ошибка Lua внутри мода (текст — без путей) |

Задача (`act`) возвращает ошибку, только если не принята. Итог принятой задачи —
событие `job_done` / `job_failed` с кодом из этой таблицы ([EVENTS.md](EVENTS.md)).
Ошибки транспорта и сервера (`transport_timeout`, `game_paused`, `repeated_failure`, `access denied`,
`response too large`) — у сервера, см. MCP.md «Ошибки сервера».

## 4. Операции
«h» — нужен живой помощник (`helper` обязателен). «h?» — `helper` необязателен, но если указан,
помощник должен быть жив. Все операции синхронные; долгая работа — только `act` + очередь.
Позиция игрока везде — `player.physical_position` / `physical_surface` (в 2.0 у игрока есть
удалённый вид, `position` показывает камеру); игрок «есть», если `connected` и `character ~= nil`.

| op | h | args | data | модуль |
|---|---|---|---|---|
| `hello` | | `{}` | `{proto:1, mod, tick, seq, owner, players_online, players:[{index,name,online,surface,pos}] (≤ 64), helpers:[id], module_errors:int, module_errors_last:[{where, text, tick}]}` (`helpers` — все не удалённые, живые и мёртвые; `module_errors` — сколько раз модуль или рефлекс упал под `pcall` с загрузки сейва; `module_errors_last` — последние 3 падения, старые первыми: `where` — место («reflex ammo», «op act», «tick follow»), ≤ 80 байт, `text` — что бросил Lua, без путей и номеров строк, ≤ 160 байт; тоже в памяти, после загрузки сейва пусто) | ядро (`core/ops.lua`) |
| `helper_spawn` | h | `{}` | `{helper, unit_number, surface, pos, at:"owner"│"respawn_point"}` | ядро (`core/registry.lua`) |
| `helper_remove` | h | `{}` | `{corpse?:pos}` — тело `die()`, вещи в трупе; для мёртвого помощника тоже можно (без трупа) | ядро |
| `helper_list` | | `{}` | `{helpers:[{id, state, body, surface?, pos?, job?, cooldown_s?, corpse?, away?}]}` | ядро |
| `helper_limit` | | `{max:1..16}` | `{max, alive}` — админская (агентам сервер её не выдаёт) | ядро |
| `helper_attach` | h | `{player:string}` | `{helper, pos, surface}` — админская; id помощника — в конверте `helper` (§7 «Два вида тела») | ядро (`core/attach.lua`) |
| `act` | h | `{do, args, replace?=false}` | `{job, queued_before}` | ядро (`core/jobs.lua`) |
| `cancel` | h | `{job?│all?:true}` | `{cancelled:[job]}` | ядро |
| `jobs` | h | `{}` | `{active?:{job,do,since,progress,req}, queue:[{job,do,req}]}` (`req` — `id` запроса, поставившего задачу) | ядро |

| `vision` | h | `{on:bool}` | `{on}` | восприятие (`perception/vision.lua`) |
| `say` | h | `{text, as?}` | `{}` — сообщение в чат от имени помощника (правила ниже) | ядро |
| `owner_hold` | h? | `{release?=false, seq?}` | без `release` — `{hold:{id:{kind, tick, seq}}}`; `release:true` (нужны `helper` и `seq` нового поручения хозяина) — `{released:[id]}`; правила — EVENTS.md «Слово хозяина» | ядро (`core/owner_words.lua`) |

| `state` | h | `{}` | STATE.md | восприятие |
| `map` | h? | `{center?│near?:"player", radius?=16 (≤32), types?, names?}` | STATE.md | восприятие |
| `resources` | h? | `{center?│near?:"player", radius?=64 (≤128), name?}` | STATE.md | восприятие |
| `stock` | h? | `{center?│near?:"player", radius?=64 (≤128), items?, limit?=50 (≤200)}` | STATE.md | восприятие |
| `ghosts` | h? | `{area?│radius?=64 (≤128), center?│near?}` | STATE.md | восприятие |
| `recipes` | h | `{filter?}` | STATE.md | восприятие |

Операция модуля, которой нет в списке требований ядра (`dispatch.HELPER_REQ`), считается «h?»;
`supply` сама требует живого помощника (без него — `no_helper`).

Правила:
- **Настройки и разрешения** (`core/perms.lua`). Хозяин задаёт в игре (Настройки → Настройки модов → Карта)
  для каждого вида действий «сам» (`auto`), «спросить» (`ask`) или «нельзя» (`deny`); таблица ключей —
  README.md «Настройки», у каких действий какие ключи — ACTIONS.md «Разрешения хозяина». Гейт стоит в `act`
  (до постановки задачи), в каждом шаге `plan` и в `reflexes` (только при включении рефлекса, которого ещё нет
  в наборе). Порядок: «нельзя» → `owner_forbids`; «спросить», а ключа нет в `owner_ok` → `needs_owner_ok`;
  иначе действие идёт как обычно. Ошибка может нести `error.data` (`{perm}`). Задача очереди помнит
  `perm_gate` и `owner_ok`: проверка при постановке — ранний отказ, а когда задача начинается, действие
  проверяет разрешения ещё раз по тому, что нашлось на месте (цель `deconstruct`, `extract`, `set_recipe`,
  `mine{target}`, плавка в `get_items`, деревья в `mine{item}`, трата `build_blueprint`, `build_ghosts`,
  `connect_entities`, `plan_belt`). Отказ на этом шаге — `job_failed` с тем же кодом и `detail.perm`.
- `act`: по умолчанию `replace=false` — задача встаёт в конец очереди. `replace=true` отменяет
  текущую и очередь (`job_failed{code:"cancelled"}` каждой). Очередь ≤ 32 ждущих задач (без
  активной), больше → `limit`. `act{do:"wait", replace:true}` → `bad_args` (`wait` никогда не
  заменяет очередь).
- **Лимит помощников.** Занятых мест (живые + ждущие возрождения + тела-игроки в `away`) ≤
  `max_helpers` (иначе `limit`), записей в `storage.helpers` ≤ 32 (удалённые записи хранятся ради
  перезарядки и чистятся, когда места не хватает). `max_helpers` задаёт игрок при запуске
  напарника («сколько помощников?»): запускающий скрипт шлёт админскую операцию
  `helper_limit {max:1..16}` → `{max, alive}`; значение лежит в `storage.proto = {version,
  max_helpers}`, по умолчанию 1. Уменьшить ниже числа занятых мест нельзя (`limit`); `alive` в
  ответе — только живые. Тело-игрок место тоже занимает.
- **h? без помощника** (операции чтения): поверхность, сила и центр берутся у хозяина
  (`physical_surface/position`); хозяина нет онлайн → `no_player`. `near:"player"` при хозяине на
  другой поверхности, чем помощник → `no_player`.
- **`helper_spawn`.** Порядок проверок: своя запись (живое тело с этим id или id привязан к
  телу-игроку в любом состоянии, кроме `removed` → `helper_exists`; своя перезарядка → `cooldown`)
  → место в лимите (`limit`) → общая перезарядка → хозяин.
  - **Перезарядка — 10 секунд, общая для всех id**, как возрождение в игре: считается от последнего
    удаления или смерти любого тела-персонажа. Раньше 10 с — `cooldown` (текст называет, сколько
    секунд ждать).
  - **Где появляется тело.** Пара remove→spawn не может служить телепортом: пока не прошло 5 минут
    после ухода любого тела-персонажа, новое тело появляется не у хозяина, а в точке возрождения
    силы (`force.get_spawn_position` на поверхности хозяина, поиск свободного места ≤ 16 клеток,
    иначе `cannot_place`) и идёт пешком — `at:"respawn_point"`. Позже 5 минут — рядом с хозяином
    (≤ 10 клеток, его поверхность, иначе `cannot_place`) — `at:"owner"`. Запись `removed` хранится
    эти 5 минут: по ней решается, где появиться телу.
  - Хозяин онлайн — нужно его тело (иначе `no_player`). Хозяин есть в сейве, но **офлайн** (сервер
    без окна в тестах) — опорой служит его последняя `physical_position` на `physical_surface`;
    хозяина нет в сейве → `no_player`.
  - Новое тело: пустой инвентарь, без брони, качество `normal`.
  - Перезарядка прежнего тела-персонажа переживает `helper_attach`/`helper_remove` того же id (поле
    `char_gone_tick`): цепочка remove → attach → remove → spawn не переносит тело к хозяину без
    ожидания. Поэтому `helper_list` у отвязанной записи может показывать `cooldown_s`.
- **`helper_list`.** `state` — `"alive"│"dead"│"away"│"removed"`; `body` — `"character"│"player"`;
  у живых `surface`, `pos` — где тело; у мёртвых `pos` — место смерти и `corpse` — где труп; у `away`
  — `pos`, `surface` (где тело было в последний раз, если известно) и `away` (причина); `job` —
  номер активной задачи; `cooldown_s` — сколько секунд до возможного `helper_spawn`.
- **`blob_put`**: `blob` — id `^[a-z0-9-]{1,32}$`, `data` ≤ 3500 байт (больше → `limit`), части
  1..`total`, любой порядок, повтор части безопасен; `total` не меняется с первой части (иначе
  `bad_args`). `storage.blobs` — живут 10 мин с последней части, всего ≤ 1 МБ (`limit`).
  Используется `build_blueprint{blob}`.
- **`say` и сообщения игроку.** Текст (до очистки ≤ 4000 символов) приводится к одной строке
  (`\n` убираются), rich-text теги `[...]` вырезаются — кроме меток карты: `[gps=x,y,поверхность]`
  собирается заново из целых (округлённых) чисел и имени поверхности, если такая поверхность есть
  (без имени — поверхность помощника); место числами в скобках «(x,y)» мод сам делает такой меткой на
  поверхности помощника; меток не больше 5. Необязательное `as` (≤ 24 байт, скобки вырезаются) заменяет имя помощника в префиксе — так сервер говорит за стратега («Стратег: …»). Затем текст обрезается до 200 символов; пустой после
  очистки → `bad_args`. Префикс — имя помощника и `: ` (без квадратных скобок, чтобы имя не сложилось
  в тег rich-text вроде `[color]`). Имя — настройка мода `partner-helper-name` (runtime-global, по
  умолчанию «Claude», ≤ 24 символов, скобки вырезаются): у `h1` — оно само, у остальных —
  «<имя> <id>». Тем же именем мод подписывает тело без игрока (надпись над головой и метка на карте
  силы, обновляются раз в 60 тиков) и красит его в цвет подписи; у тела-игрока всё это даёт сама игра.

## 5. Порядок, таймауты, повторы
- Сервер держит два RCON-соединения: `cmd` (операции агента) и `poll` (опрос `events`).
- На соединении — строго одна команда за раз, ответ сверяется по `id` (при игроке онлайн
  ответы RCON могут приходить вразнобой). Ответ **без `id`** (не JSON, плохой `id`) считается
  ответом на единственную команду в полёте и не повторяется.
- Таймаут ответа: `cmd` 10 с, `poll` 5 с. После таймаута сервер переподключается и
  **повторяет тот же `id`** (мод вернёт сохранённый ответ, действие не задвоится).
  Не удалось за 3 попытки → агенту `transport_timeout`.
- `tick` не растёт 3 с подряд → пауза (хост в меню/пауза). Изменяющие вызовы (`act`, `cancel`,
  `reflexes{set}`, `say`, `blob_put`, `owner_hold{release}`) → ошибка `game_paused` без отправки в мод (перед отказом
  сервер ещё раз спрашивает `hello` — вдруг игра уже идёт); чтение (`state`, `map`, `resources`,
  `stock`, `ghosts`, `rates`, `status`, `recipes`, `wait` и др.) → данные с полем `warning:"game_paused"`.
  Если пауза стала видна только в ответе на уже исполненный изменяющий вызов — результат с тем же
  `warning` (задача уже принята, скрывать её нельзя).
- `tick` уменьшился → игра перезагружена: событие `game_reloaded`, задачи считаются потерянными.

## 6. Честность (обязательно для всего мода)
1. **Без телепорта.** Перемещение — только `walking_state` / вождение. `teleport` в моде запрещён.
2. **Без предметов из воздуха.** Предметы — только из инвентаря помощника, из
   контейнеров/машин/земли/трупа в пределах досягаемости. `insert` в помощника — только как
   вторая половина честного переноса (остаток возвращается источнику).
3. **Досягаемость** — значения персонажа (`reach_distance`, `build_distance`,
   `resource_reach_distance`, `item_pickup_distance`) с бонусами силы. Все действия сами подходят
   к цели (ACTIONS.md «Подход»). «Вплотную» к камню, дереву, рыбе (`resource_reach_distance`)
   считается от края рамки сущности (`bounding_box`), а не от центра: у огромного камня от центра
   до края около 2 клеток.
4. **Крафт** — только `begin_crafting` (движок тратит время и ингредиенты).
5. **Стройка руками:** `LuaControl.can_place_entity` (досягаемость + коллизии) →
   `surface.create_entity{..., force, raise_built=true, quality="normal"}` → списать 1 предмет
   `remove_item{name, count=1, quality="normal"}`; не списалось → `destroy()` и `no_items`.
   **Призрак руками:** тело в `build_distance` от призрака + `ghost_revive` = true →
   `ghost.revive{raise_revive=true}` (событие `script_raised_revive`) → списать предмет; не списалось →
   постройку убрать, призрак вернуть, `no_items`. `LuaControl.can_place_entity` здесь не зовётся
   (он считает сам призрак помехой).
   **Постановка призрака:** `surface.can_place_entity{name=<inner>, position, direction, force,
   build_check_type=defines.build_check_type.manual_ghost}`. Призрак на непостроимом месте нельзя
   оставлять: дроны вечно висят над ним. **Призрак «заблокирован»**, если
   `surface.can_place_entity{name=ghost.ghost_name, ..., build_check_type=defines.build_check_type.ghost_revive}`
   = false.
   **Разбор** — `selected` + `mining_state` с ожиданием (движок тратит `mining_time`);
   `mine_entity` и `destroy`+`insert` запрещены.
6. **Чужое не трогаем.** Цели действий — только сущности силы помощника или `neutral`
   (ресурсы, деревья, камни); иначе `not_found`.
7. **Обзор, два уровня.** *Статичное* (тайлы, постройки своей силы, ресурсы, призраки) —
   в открытых чанках (`force.is_chunk_charted`). *Живое* (враги, содержимое контейнеров и машин,
   предметы на земле, прогресс машин) — только в видимых чанках: рядом с игроком или радаром
   (`force.is_chunk_visible`), **либо в радиусе 32 клеток от живого тела помощника** (его
   собственные глаза; без игроков онлайн `is_chunk_visible` от `force.chart` не включается).
   Проверка одна на всех — `require("scripts.core.vis").visible(helper_id, surface, pos)`; модули
   зовут её, а не `is_chunk_visible` напрямую. Иначе `not_visible` (для `map` — просто не показывать).
   Путь и цели `walk`/`approach` — только в открытых чанках (`not_charted`).
   **Планируем по карте, на месте перепроверяем.** В открытых чанках без текущего обзора
   планировщики (поиск пути `plan_belt`, проверки постановки) учитывают всё неподвижное, что там
   стоит, — как игрок видит это на карте в последнем известном виде: плитки, скалы, деревья, постройки
   любой силы, в том числе гнёзда и червей врага («гнездо на карте есть — обходим»). Подвижных врагов
   (юниты) не учитывают. Отличить постройку, появившуюся после последнего взгляда, мод не может — это
   принятая неточность. Наружу уходят только клетки пути: список чужих построек не отдаётся. Вторая
   половина правила — перепроверка на месте: `plan_belt{from:"resume"}` (ACTIONS.md).
8. **Обзор помощника** — `force.chart(surface, area)` вокруг **живого** тела раз в 60 тиков,
   радиус 64 клетки (2 чанка, как у игрока; окно 5×5 чанков открывается кругом — углы не
   гарантированы). Порядок — STATE.md «vision». Не идёт при смерти/удалении; `vision{on:false}`
   выключает обзор **для текущего тела** — после `helper_spawn` и возрождения обзор снова включён.
   `map{center}` никогда не вызывает `chart`.
   Помощник всегда в силе хозяина: без игроков онлайн `force.chart` открывает карту силе игрока,
   но **не** силе, созданной `game.create_force`, — отдельных сил для помощников не заводить.
9. **Появление тела.** Только `helper_spawn` (§4) с пустым инвентарём и возрождение после смерти:
   через 600 тиков у `force.get_spawn_position(surface)` той же поверхности, пустой инвентарь,
   событие `respawned` (как у игрока). Вещи остаются в трупе.
   Нет свободного места у точки появления — повтор каждые 5 с, до 12 раз, потом
   `reflex_done{type:"respawn", outcome:"failed"}` (помощник остаётся `dead`, его можно `helper_remove`).
   Мёртвый помощник, ждущий возрождения, **занимает место** в лимите `max_helpers` (§4), поэтому
   возрождение лимит не превышает.
10. **Никакого произвольного Lua** ни в моде, ни в сервере, ни в тестовом стенде.
11. **Качество (Space Age):** в v1 только `normal`. Все вызовы API с предметами и
    сущностями явно передают `quality="normal"`; предметы другого качества не видны и не трогаются.
    Исключение — рефлекс `evacuate`: постройки и модули, которые тело само разобрало, оно ставит обратно
    того же качества из своих карманов (своё поле мода `quality` у `place` и `insert`; агенту оно недоступно).
12. **Свойства мира — из игры, не из кода.** Имён плиток, планет и жидкостей в моде нет: планеты из
    модов должны работать без правок. Что откуда берётся:
    - можно ли пройти — маска столкновений плитки (`LuaTilePrototype.collision_mask`) против маски
      прототипа `character`;
    - можно ли строить — `can_place_entity` для конкретной постройки (а не «это вода»);
    - чем накрыть плитку — `LuaTilePrototype.default_cover_tile` (и `allows_being_covered`,
      `is_foundation`); каким предметом — `items_to_place_this` плитки-подложки; доступна ли подложка —
      её рецепт открыт силе **или** предмет уже есть у помощника или на складах;
    - можно ли пройти под плиткой подземным конвейером или трубой — `underground_collision_mask`
      прототипа подземной постройки против маски плитки (под лавой подземные не проходят). Во время
      игры в 2.0.77 это поле не читается, поэтому файл стадии данных `data-final-fixes.lua` кладёт
      явно заданные маски в прототип `mod-data` `factorio-partner-underground-masks`. Для прототипа
      без записи — осторожное правило: под плиткой, где сам конвейер стоять не может, подземный не
      идёт. Файл стадии данных только читает прототипы и добавляет этот один прототип `mod-data`;
      игровых прототипов не меняет;
    - подписи в ответах агенту — имена плиток как есть (`lava`, `oil-ocean-deep`…).

## 7. Хозяин, помощники, хранилище
- **Хозяин** — игрок из настройки мода `partner-owner` (runtime-global, строка; пусто → игрок
  с индексом 1). Приказы агент принимает только от хозяина (EVENTS.md `player_said.owner`).
- **Запись помощника.** `storage.helpers[id] = {entity, unit_number, state="alive"│"dead"│"away"│"removed",
  reg, spawned_tick, died_tick, died_pos, died_surface, corpse_pos, removed_tick, char_gone_tick?,
  player_index?, away?, away_pos?, away_surface?, hold?, walk_owned?}`:
  - `reg` — номер `script.register_on_object_destroyed` тела;
  - `died_surface` — поверхность смерти (нужна `helper_list` у записи, ушедшей в `away`); у записей
    из сейвов, где поля нет, запасной путь — поверхность игрока; при возрождении поле очищается;
  - `char_gone_tick` — тик, с которого идёт перезарядка после прежнего тела-персонажа этого id (§4);
  - `player_index`, `away`, `away_pos`, `away_surface`, `hold`, `walk_owned` — только у тела-игрока
    (ниже «Два вида тела»).
- **Удаление.** Ядро ставит `state="removed"` **до** `die()`, поэтому рефлекс смерти такие события
  игнорирует. При `helper_remove` и `replace` задачи — `cancelled`; `helper_remove` снимает и
  резервы, и набор рефлексов. Исчезновение тела не по смерти — `script.register_on_object_destroyed`
  → событие `helper_lost{reason:"destroyed"}`, задачи `job_failed{code:"no_helper"}`.
- **Смерть** (ядро, `on_entity_died`/`on_post_entity_died`): `state="dead"`, `died_tick`, `died_pos`,
  `died_surface`, `corpse_pos`; задачи снимаются `job_failed{code:"no_helper"}` (`stop` зовётся при ещё
  живом теле), резервы снимаются. Обработчик ядра идёт **после** модулей: рефлекс смерти
  (`scripts/reflexes/death.lua`) видит `state="alive"`. Событие `died` и возрождение делает этот
  рефлекс; новое тело он отдаёт ядру через `require("scripts.core.registry").set_body(id, entity)`,
  сам в `storage.helpers` не пишет.
- Хука «помощник появился/удалён» для модулей нет: восприятие и рефлексы смотрят
  `storage.helpers[id]` (`state`, `died_tick`, `unit_number`) сами (только чтение). Ядро отдаёт модулям
  `registry.info(helper_id) -> {body, module_errors}` (для `state`); последние падения — `err.module_errors_last()`.
- **Резерв** (для нескольких помощников): `storage.reservations = {items={[helper]={[name]=count}},
  areas={[helper]=area}, machines={[unit_number]=helper}}` (`machines` — печи, которые помощник занял
  для плавки в `get_items`, до конца шага). `collect`/`extract` не берут чужой резерв, `build_*` держат область на
  время задачи (пересечение → `reserved`). Область держат `build_ghosts`, `build_blueprint`,
  `build_layout` (с места, найденного поиском), `deconstruct{area}`; `place` и `deconstruct{target}` чужой резерв только проверяют.
- **Доступ модулей к ядру** (кроме `ctx`): чтение — `jobs.active`, `jobs.queue_len`,
  `jobs.queue_of(helper)`, `events.query`; постановка задачи рефлексом — `jobs.op_act` (только
  рефлексы). В `storage.jobs` никто, кроме ядра, не пишет. Метод `stop` действия может вернуть таблицу
  простых полей — ядро дописывает их в `detail` события `job_failed` (так приходит, например,
  `unmarked`).
- **Подключение модулей.** `control.lua` — точка входа ядра: модуль добавляется одной строкой в
  список `ACTIONS` (действие из `scripts/actions`) или `MODULES` (всё остальное, в том числе операции
  восприятия `access`, `supply`, `lookup`). Модули сами `script.on_event`, `on_nth_tick` и
  `commands.add_command` не вызывают — ядро склеивает их `M.events` / `M.on_nth` (фильтры событий
  объединяются через «или»). Отсутствующий файл из списка — ошибка сборки мода.
- **Ключи верхнего уровня `storage`:**
  - `proto` — `{version, max_helpers}`; `helpers`, `jobs`, `events`, `recent`, `blobs`, `reservations` —
    ядро;
  - `vision` — обзор (STATE.md «vision»); `reflexes` — наборы рефлексов; `reflex_state` — состояние
    рефлексов; `path_requests` — запросы поиска пути;
  - `mining_last[helper]` = `{surface, surface_index, outputs=[{pos, direction (0│4│8│12), side}] (≤ 16), tick}` —
    выходы последней разметки `plan_mining`; их читает `plan_belt{from:"patch"}`. `helper_remove`
    запись не чистит, читатель проверяет поверхность и тик;
  - `belt_last[helper]` = `{surface_index, to, belt, underground, lanes, cells (позиции призраков плана
    по лентам, ≤ 4096), tick}` — последний план `plan_belt`; его читает `plan_belt{from:"resume"}`.
    План длиннее 4096 клеток не запоминается (`from:"resume"` ответит `bad_args`);
  - `layouts[helper]` = `{[tag] = {surface, anchor:{x,y}, direction, tick, placed:[{i, name, pos}] (≤ 100),
    ports:{[id] = {pos, dir, kind, io, items?, fluid?}}}}` — память поставленных блоков: пишет только
    `build_layout` с `tag` (не в `dry_run`), читает `connect_entities` (концы `{layout, port}` и
    `{layout, i}`) через `scripts/lib/layout.lua`. `placed` — и постройки, которые уже стояли
    (`exists`). Не больше 16 тегов на помощника (старший по `tick` вытесняется); записи удалённого
    помощника снимаются при следующей записи и раз в 10 с. Сущностей не хранит — только имя и место;
  - `connect_last[helper]` = `{sig, surface, area, cells (≤ 400)}` — последняя прокладка
    `connect_entities`: пишет и читает только она (возврат после отступления без нового поиска);
  - `connect_fled[helper]` = `{sig, tick, surface, force, flat:[{x, y, name, w?, placed?, marks?}]}` —
    свои призраки и пометки к сносу прокладки, снятой отступлением `flee`. Задача с той же подписью
    подхватывает их по `connect_last`; другая прокладка помощника или 5 минут без возврата — убираются;
  - `nameplates` — подписи и метки карты тел без игрока (§4 «say»), `bg_crafts` — фоновые крафты
    `craft{wait:false}` (EVENTS.md `craft_done`) — заводятся модулями по требованию.

  Все ключи, кроме `nameplates` и `bg_crafts`, создаёт `scripts/core/migrate.lua` (`ensure_shape`,
  пустыми таблицами); миграции — там же. Модуль пишет только под своим ключом.
- В `storage` можно хранить LuaEntity (API это позволяет), но рядом — `unit_number`, и перед
  использованием проверять `valid`. Функции в `storage` не класть.
- **Инвентарь тела без игрока** мод раз в 300 тиков сортирует `sort_and_merge` (как кнопка
  сортировки: порядок ячеек и слияние стопок, ни предмета больше или меньше) — у тела без игрока нет
  настройки автосортировки. Тело-игрок не трогается: у него своя настройка в игре.

### Два вида тела
Флаг запуска напарника `--body character│player`, по умолчанию `character`.
- `character` — тело без игрока, создаёт `helper_spawn` (всё описанное выше). Основной режим.
- `player` — тело **подключённого второго клиента** игры: админская операция
  `helper_attach {player:string}` → `{helper, pos, surface}` привязывает помощника к персонажу этого
  игрока (`storage.helpers[id].player_index`). Все действия идут тем же кодом по `player.character`.
  Зачем: у тела-игрока работает то, что игра и чужие моды дают только игроку (рамки выделения,
  окна модов). Управление рамкой — отдельный слой ввода на стороне клиента, **в v1 его нет**.
- **`helper_attach`:** имя игрока — точное (≤ 60 символов); игрока нет в сейве, он офлайн, без
  персонажа, хозяин или не в силе хозяина → `no_player`; игрок уже привязан к другому помощнику или id
  занят живым телом → `helper_exists`; нет места в лимите → `limit`; запись с мёртвым телом-персонажем
  заменяется (его возрождение отменяется). Перезарядки у привязки нет. `helper_spawn` и `helper_attach` на
  id, привязанный к телу-игроку (в том числе в `dead` или `away`), отвечают `helper_exists` (и для
  того же игрока); освобождает только `helper_remove`.
- **Отличия тела-игрока:**
  - состояния ходьбы и добычи мод выставляет **каждый тик** (ввод клиента их сбрасывает);
  - карту открывает и возрождает движок (обзор §6.8 и возрождение §6.9 для такого тела мод не
    делает); после возрождения мод берёт новый `player.character` сам — событие `respawned{pos}`;
  - игрок вышел из игры → задачи `job_failed{no_helper}`, событие `helper_lost{reason:"player_left"}`,
    запись получает `state="away"`, `away=<причина>`, `away_pos`/`away_surface` (место в лимите
    держится, операции «h» отвечают `no_helper`); вернулся — тело подхватывается снова, событие
    `respawned{reason:"player_joined"}`. Игрок вышел, пока тело мертво, — запись тоже уходит в `away`
    с `helper_lost{player_left}`; причина `away` меняется с `no_character` на `player_left` без второго
    `helper_lost`;
  - персонажа нет при игроке онлайн (редактор, режим бога, катсцена) или он подменён —
    `helper_lost{reason:"no_character"│"body_changed"│"destroyed"}`, `state="away"`, потом подхват с
    `respawned{reason:"body_restored"}`; игрока удалили из сейва — `helper_lost{reason:"player_removed"}`,
    запись `removed`. Ядро каждый тик сверяет запись с игроком, поэтому пропущенное событие движка
    ничего не ломает;
  - `helper_remove` только отвязывает: персонажа игрока не убивает, трупа и перезарядки нет, сразу
    можно `helper_attach` снова;
  - подписи над головой, метки на карте и автосортировки мод для такого тела не делает.
- **Удержание и ввод человека.** Мод держит только то состояние, которое выставило **активное
  действие** (`hold = {job, walking, direction, mining, mining_pos, selected, selected_unit}` пишет ядро
  после действий; `selected_unit = false` — добыча без выбранной сущности):
  - **ходьба:** пока у помощника есть задача (активная или в очереди), каналом ходьбы управляет
    только мод: ходьбу, включённую не активным действием, он выключает и после тика **не
    возвращает** — отличить клавишу человека от собственного прежнего движения нельзя, а возврат
    сделал бы движение вечным (тело дрейфовало бы). Если задача кончилась между тиками (отмена,
    замена, отказ), а ходьбу включал мод (`walk_owned`), он один раз её выключает;
  - **добыча:** добычу, включённую человеком, мод на время действия выключает и после тика
    возвращает нетронутой;
  - без задачи мод телом не управляет вовсе: человек за вторым клиентом ходит сам.

## 8. Ходьба: поиск пути и застревание
Общие правила модуля пути (`scripts/lib/path.lua`) для всех действий, которые ходят; как действия
подходят к цели — ACTIONS.md «Подход».
- **Коробка поиска пути** — тело из прототипа персонажа (`collision_box`) плюс 0.15 с каждой
  стороны (у ванильного ±0.35 против ±0.2; тела нет — ±0.35). Моды, меняющие рамки построек
  (например, Squeak Through 2), учитывает сам движок поиска пути.
- **Два маршрута сразу.** Первый запрос пути задачи идёт парой: широкая коробка и настоящая коробка
  тела («тонкий» маршрут). Тонкий берётся, если он короче широкого хотя бы на 20 % и на 2 клетки (или
  широкого нет; ответа на тонкий ждут до 120 тиков после широкого): так помощник идёт сквозь щели
  между машинами, а не в обход. Дальнейшие пересчёты задачи — выбранным способом.
- **Старт от препятствия.** Тело вплотную к постройке или жидкости → широкий запрос не находит пути;
  тогда один повтор с настоящей коробкой тела, по нему тело только отходит на 1.5 клетки, после чего
  путь считается заново широкой коробкой. Не нашёлся и он — к цели ведёт только узкий проход: тело
  идёт тонким маршрутом до конца, перепланирования этой задачи — тоже тонкие.
- **Пути нет с самого начала.** Не нашёлся ни широкий, ни тонкий путь — до отказа тело один раз за
  задачу выбирается из зоны (как при застревании, ниже), потом путь ищется заново; снова нет —
  `failed{path_failed}`. Ходьбы рефлексов (`req` вида `reflex:…`) это не касается: бегство само
  переберёт другие точки отхода.
- **Застревание** — тело не сдвинулось на 0.1 клетки за 60 тиков, **или** «ёрзает»: за 180 тиков не
  приблизилось к текущей точке маршрута (на последнем отрезке — к цели) хотя бы на 0.3 клетки и не
  перешло к следующей точке. Пока цель движется (`follow`, `approach` к игроку), отсчёт ёрзания
  сбрасывается.
- **Выбирание из застревания.** Маршрут не пересчитывается сразу (он чаще всего снова ведёт в тот же
  угол): тело ищет выход из «зоны» — круга 2.5 клетки вокруг места застревания — короткими проходами
  по восьми сторонам, от ближних к нужному направлению (±45°, ±90°, ±135°, назад, вперёд); сторона
  упёрлась (не сдвинулось 15 тиков) — следующая сторона с того места, где стоит. Вышло из круга — путь
  заново. Не вышло за 15 с или застряло в той же зоне третий раз — `failed{stuck}`. Шумное
  `stuck{reason:"no_progress"}` — одно на выбирание. Только ходьба.
- **`follow` вблизи** — хозяин ближе 8 клеток: помощник идёт к нему напрямую, без запроса пути;
  прямо не идётся (не сдвинулся 20 тиков) — 5 с обычный поиск пути.
