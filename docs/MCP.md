# MCP-сервер `factorio_partner`

Тонкий MCP-слой над `core.py`, который проверяет аргументы и ходит в мод по RCON
(протокол — [PROTOCOL.md](PROTOCOL.md)). Python ≥ 3.11, `mcp>=1.12,<2` (FastMCP, stdio).
Один процесс сервера на всех помощников. Запуск: `python -m factorio_partner.server [--admin]`;
stdout принадлежит протоколу MCP, журналы — только в файлы (раздел «Логи»).

## Слои
- `rcon.py` — RCON-клиент на библиотеке `factorio-rcon-py` (`AsyncRCONClient`): одна команда за раз
  на соединение, ответ декодируется как UTF-8 с `errors="replace"`; любой сбой закрывает сокет,
  следующий вызов переподключается.
- `bridge.py` — два соединения (`cmd`, `poll`), конверт v1, таймауты и повторы по PROTOCOL §5
  (повтор — тем же `id`), детект `game_paused` и `game_reloaded`.
- `core.py` — `op_*`: ключ помощника, белые списки `do` и полей, лимиты, курсоры событий,
  защита от зацикливания, загрузка чертежей частями (`blob_put`), заметки по сейвам. Ничего не
  знает про MCP.
- `roles.py` — роли ключей и права на инструменты (раздел «Роли»); `poller.py` — общий опрос
  событий мода для всех `partner_wait` одного помощника.
- `ledger.py` — файл пакетов стройки сейва; `orders.py` — мост пакетов: сам ставит пакет телу и
  проверяет результат (раздел «Пакеты стройки»).
- `validate.py` — проверки аргументов до похода в мод; `savenotes.py` — файлы правил и памяти
  (`partner_notes`); `brief.py` — ответ `partner_brief`; `forge.py` — связка с factorio-forge
  (`partner_plan`).
- `server.py` — инструменты MCP; `PartnerError` → `ToolError` (агент видит `code` или `code: text`).
- `cli.py` — JSON из stdin → JSON в stdout теми же `op_*` (отладка; флаг `--admin` — служебные).

## Доступ и настройки
- `FP_HOME` — папка данных сервера, по умолчанию `%LOCALAPPDATA%\factorio-partner` (без
  `LOCALAPPDATA` — `~/.local/share/factorio-partner`), вне репозитория.
- RCON: `FP_RCON_HOST` (только `127.0.0.1`/`localhost`, `localhost` превращается в `127.0.0.1`; иное —
  отказ запуска), `FP_RCON_PORT` (по умолчанию 27015), `FP_RCON_PASSWORD_FILE`. Пароль читается из
  файла при подключении, не логируется и не попадает в ответы. Файл пароля — одна строка;
  снимаются только BOM и `\r\n` в конце, пробелы по краям — часть пароля (кто пишет файл, пробелов
  не добавляет).
- Ключи помощников: `FP_HOME/helpers.json` = `{"h1": "<32+ символа>"}` (ключ 32–256 символов) —
  ключ пилота; или `{"h1": {"voice": "<ключ>", "pilot": "<ключ>", "strategist": "<ключ>"}}` — у
  каждой роли свой ключ (любой можно не задавать; раздел «Роли»). Общая запись `"*"` —
  `{"voice": "<ключ>", "strategist": "<ключ>", "host": "<ключ>"}`: один голос и один стратег на всех
  помощников сервера (раздел «Несколько помощников»); `host` — ключ диспетчера, который передаёт ролям
  слова хозяина из главного чата (раздел «Хозяин через главный чат»). Инструменты принимают `helper` + `key`, сравнение
  `hmac.compare_digest` со всеми ключами помощника и общей записи, любая ошибка доступа — один
  текст `access denied`. Ключи выдаёт запускающий скрипт (`agents/launch.py`) — каждому агенту
  только его ключ. Риск «ключ виден в контексте и транскриптах» принят: всё локально, защищаемся от
  путаницы помощников, а не от взлома.
- Три разные настройки forge: `FP_FORGE` — папка **с кодом** forge (checkout пакета `factorio-forge`);
  `FACTORIO_FORGE_HOME` — папка **данных** forge (профили, `notes.md`), по умолчанию
  `%APPDATA%\factorio-forge`; `FP_FORGE_PROFILE` — имя профиля сейва (по умолчанию — активный
  профиль forge). В конфиге стенда им соответствуют ключи `forge`, `forge_home`, `forge_profile`
  (TESTING.md). Сервер **никогда не активирует** профиль: активный профиль — общее состояние venv
  forge и решение хозяина. Задан `FP_FORGE_PROFILE`, а активен другой → `partner_plan` отвечает
  `{supported:false, reason}`.
- Заметки по сейвам (`partner_notes`): `FP_NOTES_DIR` — папка, по умолчанию `save-notes/` в корне
  репозитория (в `.gitignore`: это записи хозяина); имя сейва — `FP_SAVE_NAME`, иначе
  `FP_FORGE_PROFILE`, иначе активный профиль forge, иначе `default` (имя —
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`). Там же, в папке сейва, — пакеты стройки (`packages.json`,
  раздел «Пакеты стройки»).
- Стиль общения — `FP_HOME/style.md` (≤ 4 КБ, длиннее обрезается); его отдаёт `partner_brief`.
- Процесс сервера для агентов запускается **без** `--admin` (служебные `admin_*` ключа не требуют).

## Роли
Одним помощником могут управлять три агента сразу; роль задаёт ключ (`helpers.json`, выше), её
называет `partner_brief` (поле `role`). Ключ старого вида (строка) — пилот: один агент без ролей
работает как раньше.

| роль | что может | чего не может |
|---|---|---|
| `voice` (голос) — отвечает хозяину в чате | чтение, `partner_say`, `partner_order`, `partner_cancel{all:true}`, запись правил хозяина (`partner_notes` с `kind:"rules"`), `partner_ledger{action:"thoughts"}` | любые действия тела, `partner_cancel{job}`, `partner_hold{release}`, `partner_reflex{set}`, запись `memo`, `partner_plan`, `partner_inbox{ack}`, запись `partner_ledger` |
| `pilot` (пилот) — тело | всё, кроме `partner_order` и записи пакетов; `partner_ledger{action:"cancel"}` — снять пакет; `partner_ledger{action:"ask"}` — вопрос хозяину о своём теле (раздел «Разрешения хозяина») | `partner_order`, `partner_ledger{put│resume│note│thoughts│scale}` |
| `host` (диспетчер, не агент) — слова хозяина из главного чата | `partner_relay`, `partner_rescale` | всё остальное, в том числе чтение |
| `strategist` (стратег) — планы | чтение, `partner_plan`, `partner_inbox{ack}`, проба `partner_act` с `dry_run:true`, пакеты стройки (`partner_ledger` — `put`, `resume`, `cancel`), заметка о ходе работы и вопросы хозяину (`partner_ledger` — `note`, `ask`, только стратег); шаги пакета мост исполняет телом с правами пилота, но только шаги стройки (ниже «Пакеты стройки») | прямые действия тела (`partner_act` без `dry_run`), `partner_cancel`, чат, `partner_order`, запись `partner_notes`, `partner_hold{release}`, `partner_reflex{set}`; в пакете — разбор построек хозяина, а изъятие у него — только с его разрешения (`approved`) |

- Чтение — `partner_brief`, `state`, `map`, `resources`, `stock`, `find`, `status`, `access`,
  `ghosts`, `rates`, `recipes`, `supply`, `lookup`, `wait`, `inbox` без `ack`, `notes` с
  `action:"list"`, `hold` без `release`, `reflex` без `set`, `ledger` с `action:"list"`. Любое другое
  значение этих аргументов — запись.
- Узкие формы. `partner_cancel{all:true}` без `job` — снять все задачи помощника: так голос исполняет
  «стоп» в свободной форме, которое мод не узнал как слово. Правила хозяина голос пишет потому, что
  каждая запись требует сообщения хозяина и его «да» (ниже «partner_notes»). Проба стратега —
  `partner_act` с `do` из `plan_mining`, `plan_belt`, `build_blueprint`, `build_layout`,
  `connect_entities`, `args.dry_run` ровно `true`
  (не `1` и не `"true"`) и без `replace`: мод только считает и ничего не ставит.
- Права проверяются до проверки аргументов и до похода в мод: вызов вне прав роли — отказ
  `not_allowed` (`<инструмент> is not allowed for role <роль>`), в мод ничего не уходит.
- **Ожидание по ролям.** У каждой пары (помощник, роль) свой курсор событий, свои уведомления
  сервера и своя очередь `partner_wait`: роли ждут одновременно и не забирают события друг у друга.
  Что отдаёт `partner_wait` роли:
  - пилот — всё, как раньше (громкие будят, шумные — выборка последних 6), плюс `order` и события
    пакетов `package_started`, `package_paused`, `package_verified`, `package_unmet`, `package_failed`;
  - голос — `player_said`, `owner_stop`, `owner_resume`, `game_reloaded`, `budget_low` (сервер, см. «Сторож лимита»),
    `strategist_question` (сервер, ниже «Вопросы стратега хозяину»; вопрос пилота — с `from:"pilot"` и `helper`), `strategist_note` (сервер, ниже «Мысли стратега»),
    `host_message` (сервер, ниже «Хозяин через главный чат»), `follow_lag` (мод: `follow` отстал от хозяина),
    `owner_panel` (мод: хозяин нажал в окне панели, EVENTS.md «Панель хозяина»), `rescale` (сервер, ниже «Перезапуск на другое число помощников»),
    `task_report` и `evacuate_started`, `evacuated`, `evacuate_restored`, `evacuate_missing` (ниже «Задания стратега пилоту»; EVENTS.md «evacuate»);
  - стратег — `order`, `plan_done`, `owner_stop`, `owner_resume`, `died`, `helper_lost`,
    `game_reloaded`, `package_paused`, `package_verified`, `package_unmet`, `package_failed`, `rescale`,
    `task_report`, `evacuate_started`, `evacuated`, `evacuate_restored`, `evacuate_missing`;

  Остальные события роль пропускает: курсор проходит мимо них. Счётчик `repeated_failure` ведётся
  только по событиям, отданным пилоту.
- **Общий опрос.** Ожидания всех ролей помощника опрашивают мод одним запросом `events`: сервер
  держит недавние события помощника (до 1000) и дозапрашивает только новые; одновременно в моде
  не больше одного такого запроса на помощника. Первый опрос каждого `partner_wait` берёт только
  страницу, запрошенную после начала вызова, поэтому `timeout:0` видит всё, что было до вызова;
  курсор старше запомненного (первое ожидание, отставшая роль) читается у мода напрямую.

### Несколько помощников
Один голос и один стратег могут вести всех помощников сервера, пилот — у каждого тела свой.
- **Ключи.** Ключи голоса и стратега лежат в общей записи `"*"` файла `helpers.json` (`"*"` не бывает
  id помощника); запись помощника — `{"pilot": "<ключ>"}`. Общий ключ открывает свою роль для любого
  помощника сервера — того, у кого в `helpers.json` есть ключ пилота, — и только её: права те же, что
  в таблице выше. Ключ пилота открывает только своё тело: пилот `h1` с `helper:"h2"` получает
  `access denied`. Роль `pilot` в общей записи не действует. Общий ключ, совпавший с любым другим
  ключом файла (другой ролью, пилотом какого-нибудь помощника), не открывает ничего. Прежняя схема —
  ключи ролей в записи помощника — работает как раньше, с курсором этого помощника.
- **Общий ключ действует для всех тел файла**, в том числе для тела, запущенного отдельно со своим
  ключом пилота: общий стратег может поставить пакет и ему. Исключение — помощник со своим ключом
  голоса или стратега: ему общие ключи не служат (`access denied`), одного помощника ведут либо его
  голос и стратег, либо общие, без смеси. Запуск `agents/launch.py` без `--roles` убирает запись `"*"`:
  ключи общих голоса и стратега прежнего запуска перестают действовать.
- **`helper` в вызове** общего голоса и стратега — тело, о котором речь: от его имени `partner_say`,
  его `partner_state`, его задачи снимает `partner_cancel{all:true}`, на него ставит пакет
  `partner_ledger{action:"put"}`.
- **Один курсор на всех.** У общего голоса и общего стратега один курсор и одна очередь ожидания,
  какой бы `helper` они ни передали. Их `partner_wait` читает события всех помощников одним запросом
  `events` без `helper`: событие мира (`player_said`, `owner_stop`, `owner_resume`) приходит голосу
  **один раз**, а не по разу на каждое тело; события тел (`died`, `helper_lost`, `plan_done`)
  приходят стратегу с полем `helper`. Набор событий роли — тот же, что выше. Пилоты ждут каждый на
  своём курсоре, как раньше.
- **Новое поручение снимает «стоп» и «иди сюда».** `partner_order` (не ответ на вопрос) сам снимает hold хозяина
  с тех тел, кому оно: именованного, выбранного сервером или — у поручения стратегу без имени — со всех; мод
  проверяет сообщение так же, как у `partner_hold{release}`. Ответ — `released: [id]`. Пакет, который не может
  начаться из-за hold, один раз будит голос событием `package_waits` (`data:{package, name, reason:"owner_hold",
  hold, helper}`): хозяин узнаёт, что работа ждёт его слова.
- **Уведомления сервера** (`order`, `strategist_question`, `strategist_note`, события пакетов) идут
  ролям помощника и общим голосу и стратегу; событие, не связанное с телом, — только общим (`helper:null`).
- **Общее у стратега.** Его заметка о ходе, вопросы хозяину и флаг мыслей — одни на всех (хранятся
  под `"*"` в `packages.json`), с любым `helper` вызова. `partner_inbox` общего голоса и стратега —
  поручения всех помощников и общие входящие стратега, у каждого поле `helper` (`null` — тело не
  названо); `ack` снимает поручение, в каких бы входящих оно ни лежало. `partner_ledger{action:"list"}`
  общего стратега — пакеты всех тел (у каждого `helper`); `list` с `id`, `cancel` и `resume` находят пакет
  любого тела. Пилот видит и снимает только пакеты своего тела.
- **`partner_brief`** общих ролей несёт ещё `bodies` (ниже «partner_brief»): что делает каждое тело.

### `partner_order`
Голос кладёт поручение хозяина во входящие помощника: `{said_seq, text, size:"small"│"large",
urgent?=false, answer_to?, to?}`.
- `said_seq` — номер **настоящего** сообщения хозяина. Сервер сам читает это событие у мода
  (`events{since: said_seq-1, limit:1}`) и принимает только `player_said` с `owner:true`, без
  `auto_reply` (мод уже ответил на него как на слово — «стоп», «что делаешь», «продолжай»), не старше
  10 минут игры. Иначе `bad_args`. Одно сообщение — одно поручение: повтор того же `said_seq`
  (и одновременный вызов с ним же) → `bad_args`. Использованные номера сервер помнит в памяти
  процесса, поэтому сообщение, пришедшее до первого вызова сервера или до загрузки сейва (`said_seq`
  не больше курсора на тот момент), тоже `bad_args`: стало ли оно поручением раньше, неизвестно.
- `text` — пересказ голоса одной строкой, ≤ 300 символов (`limit`); « » заменяются на `"`,
  «хозяин:» — на «хозяин -». Слова самого хозяина сервер берёт из события и кладёт в поле
  `owner_said` (≤ 500 символов): решает пилот или стратег по ним, а не по пересказу.
- `size`: `small` — одно-два действия (принеси, иди, положи) — делает пилот; `large` — стройка,
  проект — для стратега. `urgent` — хозяин сказал «срочно».
- Ответ: `{order:{id, said_seq, tick, size, urgent, text, owner_said, helper?, helpers?}, open, to}`.
  Открытых поручений во входящих ≤ 20; больше → `limit` (сообщение при этом не тратится, голос
  говорит хозяину). `to` — куда ушло: `{helper, role:"pilot"│"strategist", by}`.
- **Адресат.** Голос одного помощника (ключ в его записи) кладёт поручение в его входящие
  (`by:"own"`), `to` ему не разрешён (`bad_args`). Общий голос адресата не выбирает сам — сервер берёт
  его из слов хозяина в событии (те же правила, что у слова хозяина в моде, EVENTS.md: имя в начале
  или в конце сообщения — `Claude` это `h1`, `Claude h2`, `claude2`, `claudeh2`, `h2`; имя помощника —
  `FP_HELPER_NAME`, по умолчанию `Claude`, как настройка мода `partner-helper-name`):
  - назван один помощник — его входящие (`by:"name"`);
  - не назван никто, голос передал `to` (id помощника сервера; иначе `not_found`) — его входящие
    (`by:"to"`); `to` при названном другом помощнике — `bad_args`, `to`, совпавший с названным, принимается;
  - тело, названное по имени или через `to`, о котором игра не отвечает (погибло, пропало), — `not_found`;
  - никто и без `to`: `small` — самому свободному телу (по op `state` каждого: задача + очередь +
    открытые поручения + активные пакеты; `by:"free"` — всё по нулям, иначе `"least_busy"`; тело, о
    котором игра не ответила, и тело, которое хозяин держит словом «стоп» или «иди сюда» (op
    `owner_hold`), пропускаются; не осталось ни одного — `not_found`); `large` — общие входящие
    стратега (`helper:null`, `by:"strategist"`);
  - названо несколько: `small` — `bad_args` (сообщение не тратится), `large` — стратегу с полем
    `helpers` (кого назвал хозяин);
  - `answer_to` — всегда стратегу (`by:"answer"`).
  В поручении общего голоса есть `helper` — чьи это входящие (`null` — общие входящие стратега).
- Пилоту и стратегу этого помощника, которые уже обращались к серверу, приходит громкое событие
  сервера `order` (`helper` — помощник, `data` — поручение, как в ответе), а в ответе их
  `partner_wait` — поле `inbox` (сколько открытых поручений), пока входящие не пусты. Общему
  стратегу — каждое `order` всех помощников, `inbox` — сумма по всем входящим; поручение из общих
  входящих — только ему.
- `answer_to` — id открытого вопроса стратега (`q<N>`, ниже «Вопросы стратега хозяину»), на который
  это сообщение хозяина отвечает. Тогда `size` только `large` (иначе `bad_args`), нет такого
  открытого вопроса — `not_found`. Поручение несёт поле `answer_to`, событие `order` получает только
  стратег, пакеты оно не держит и шедший пакет не приостанавливает; вопрос закрывается (`answered`)
  до того, как поручение ляжет во входящие, поэтому второй ответ на тот же вопрос — `not_found`.

### Хозяин через главный чат (`partner_relay`)
Хозяин может писать ролям не из игры, а в главный чат Claude Code на ПК — тот, что запускает роли
(диспетчер): «передай стратегу: …», «передай пилоту Claude2: …». Диспетчер передаёт его слова
инструментом `partner_relay{helper, to, text}` с ключом `host`:
- ключ `host` лежит в общей записи `"*"` и открывает **только** `partner_relay` и `partner_rescale` — ни
  чтения, ни тела, ни `partner_order` (`not_allowed`); роли эти два инструмента не могут. Ключ годится для любого
  помощника сервера (у кого есть ключ пилота). `agents/launch.py` кладёт его в файл сессии отдельно
  (`host`), в первые сообщения ролей он не попадает;
- `to` — `voice`│`pilot`│`strategist`, роль, которую хозяин назвал; без `to` — `bad_args` (диспетчер
  роль не угадывает). `text` — слова хозяина, ≤ 600 символов (`limit`). `helper` — тело: для пилота —
  чей пилот, для голоса и стратега — о каком теле речь; помощника нет на сервере — `not_found`;
- `pilot` — поручение `{id, from:"host", tick, size:"small", text, owner_said, for}` во входящие
  помощника (событие `order` пилоту и стратегу, как у `partner_order`); `strategist` — то же с
  `size:"large"`, и шедший пакет встаёт на границе шага, как от крупного поручения голоса. Входящих
  больше 20 — `limit`. У поручения нет `said_seq`: хозяин набрал его сам, не в игре;
- голосу (своему и общему) при любом `to` — громкое событие сервера `host_message`
  `{from:"host", to, helper, text, order?}`: голос коротко говорит в чат «Из главного чата для
  <роль>: …»; при `to:"voice"` слова — ему самому;
- ответ: `{to, helper, order?, tick, seq}`.
Поручение `from:"host"` роли исполняют как слово хозяина (`partner_brief.work.orders[].from`).

### `partner_inbox`
`{ack?: [id]}` → `{orders:[…], acked?:[id], tick, seq}` — открытые поручения помощника, старые
первыми (общим голосу и стратегу — всех помощников, раздел «Несколько помощников»). `ack` (1–20 id; пилот и стратег) убирает сделанные или взятые в работу; неизвестный id —
`bad_args`. Входящие живут в памяти процесса сервера: перезапуск сервера их очищает, загрузка сейва
(`game_reloaded`) — тоже: поручения относятся к оставленной линии игры, а номера сообщений мода после
загрузки идут заново.

### Задания стратега пилоту
Всё, что требует тела и не является стройкой пакетом (дежурство, взять броню, принести, охранять,
заправить, включить рефлекс `evacuate`), стратег поручает пилоту инструментом `partner_task`:
- `give{to, text ≤ 600, duty?, area?}` — `{task:{id:"t<N>", from:"strategist", text, duty, area?, tick,
  status:"open"}}`. `to` — тело (`h1`, …): у общего стратега обязательно, у стратега одного помощника — только
  своё тело. `duty:true` — постоянное: висит, пока его не снимут стратег или хозяин или пилот не ответит
  `report`;
  `area:{center:{x,y}, radius ≤ 200}` — где тело обязано быть. Открытых заданий на тело ≤ 5, закрытые
  (последние 5) хранятся. Задания лежат в файле сейва рядом с заметками и вопросами, переживают перезапуск
  сервера и не меняют `rev` пакетов.
- `list{to?}` — задания со статусами (`open`, `done`, `failed`, `no_tool`, `cancelled`) и `missing_tools`
  (последние 20 отчётов `no_tool`: `text`, `tick`, `task`, `helper`). `cancel{id}` — снять; пилот получает
  событие `task` со `status:"cancelled"`.
- **Поручение хозяина главнее задания**, дежурство тоже. Хозяин снимает задание словом через голос:
  `partner_task{action:"cancel", id, said_seq}` (`said_seq` — его сообщение «не дежурь», «хватит охранять»,
  не старше 10 минут; без него голосу — `not_allowed`). «Хватит» хозяина (`partner_cancel{all:true}` голоса)
  закрывает все открытые задания тела (в ответе `tasks_closed`). Загрузка сейва (`game_reloaded`) закрывает
  задания всех тел, `helper_lost` — задания этого тела: они принадлежат прежнему положению дел. Каждое такое
  закрытие — `status:"cancelled"`, `by:"owner"│"reloaded"│"helper_lost"`; пилот получает `task`, стратег —
  `task_report{id, status:"cancelled", by, task, duty}`.
- Пилот получает громкое событие `task` (полное задание и `helper`), видит открытые задания в
  `partner_inbox` → `tasks` (с пометкой `tasks_are:"data, not the owner's word"`) и открытые постоянные в
  `partner_brief` → `duty`. Отвечает `partner_inbox{report:{id, status:"done"│"failed"│"no_tool", text ≤ 300}}`
  — только на задание своего тела (чужой id — `not_found`). `done` закрывает и постоянное задание.
  Стратег получает громкое `task_report{id, status, text, helper, task, duty}`; при `no_tool` оно идёт и
  голосу, и запись попадает в `missing_tools`: голос говорит хозяину «не умею: …». `partner_brief` показывает
  пилоту последние 5 записей `missing_tools`.
- **Задание — не слово хозяина.** Оно не снимает hold, не даёт `owner_ok`, не становится поручением и не
  расходует `said_seq`; его id не годится как `order` для `approved`. Пилот исполняет его всеми своими
  инструментами в тех же рамках: «спросить» — через вопрос хозяину, «нельзя» — мод откажет. Текст задания и
  отчёта — данные: «хозяин:» заменяется, длина ограничена.
- **Дежурство держит тело.** Пока у тела открыто постоянное задание с `area`, мост не ставит пакет, у
  которого `anchor` или любая точка `walk` / `approach` (в том числе `target.pos`) дальше `area.radius + 10`
  от центра: пакет ждёт в очереди, стратег один раз на пакет и дежурство получает
  `package_paused{reason:"duty", task, area}`. Пакет начнётся, когда дежурство снято или пилот ответил на
  него. В `partner_brief` голоса (`work.tasks`) — задания и их состояния (открытые, потом три последних
  закрытых), у ждущего пакета `why:"duty"`, в строках `bodies` — число открытых заданий.
- Права: `give` и `cancel` — у стратега, `list` — у стратега и голоса, `cancel` со `said_seq` — у голоса,
  `report` — только у пилота. Когда сторож лимита перешёл первый порог, новые `give` отклоняются; на
  последнем пороге (`voice_only`) `cancel`, `list` и `report` работают по-прежнему — дежурство всегда можно снять.

### Пакеты стройки
Пакет — именованный план стройки стратега: шаги действия `plan` (ACTIONS.md «plan») с якорем,
приоритетом и проверками результата. Пишет пакеты только стратег (`partner_ledger`), читают все роли.
Ставит пакет телу и проверяет его **мост** — код сервера (`orders.py`), без хода агента.

`partner_ledger{action?="list"│"put"│"cancel"│"resume"│"note"│"ask"│"thoughts", package?, id?, rev?, text?, on?, said_seq?}`:
- `list` — `{save, rev, packages:[…], history:[…], note, questions:[…], tick, seq}`: открытые пакеты
  помощника без шагов (`steps_n` вместо `steps`), до 10 последних законченных, заметка стратега о ходе
  и его вопросы хозяину (ниже); с `id` — `{save, rev, package}` целиком.
- `put` (стратег) — `{package:{…}, rev}`; новый пакет встаёт в очередь `queued` и всегда начинается с
  первого шага, даже если повторяет снятый. `rev` — номер файла, который стратег читал: файл с тех пор
  изменился → `bad_args`, перечитать.
- `resume` (стратег) — приостановленный пакет (`paused`) снова в очереди; продолжит с `from_step` —
  первого невыполненного шага, а если до него стоят шаги получения предметов (`get_items`, `collect`,
  `extract`), — с первого шага последней такой цепочки перед ним: принесённое ими за время стоянки
  могло уйти. Так же продолжает пакет и после «продолжай» хозяина, и после крупного поручения.
- `cancel` (пилот и стратег) — `{cancelled, was, job?, warning?, rev}`: пакет снят; если его план
  шёл — план снимается сразу (`cancel{job}`).
- `note` (стратег) — `{note:{text, at, tick}}`: заметка о ходе работы, одна строка ≤ 200 символов
  (`limit`; « » → `"`, «хозяин:» → «хозяин -»). У помощника одна последняя заметка: новая заменяет
  старую. Голос пересказывает её хозяину из `partner_brief` → `work.note`.
- `ask` (стратег) — `{question:{id, text, status:"open", at, tick, order?}, open}`: вопрос хозяину, ≤ 200
  символов, те же замены; открытых вопросов у помощника ≤ 5 (`limit`). `order` (только с `ask`) —
  поручение `o<N>`, о котором вопрос: ответ хозяина станет разрешением пакету этого поручения забрать у
  него (ниже `approved`). Ниже «Вопросы стратега хозяину».
- `thoughts` (голос) — `{thoughts:bool}`: хозяин включает или выключает показ мыслей стратега. `on` (bool) и
  `said_seq` обязательны; `said_seq` — настоящее сообщение хозяина, сервер читает его у мода так же, как
  у `partner_order` (`player_said`, `owner:true`, не `auto_reply`, не старше 10 минут), иначе `bad_args`;
  подтверждение «да» не нужно. Флаг у каждого помощника свой, по умолчанию выключен, хранится в
  `packages.json` (поле `thoughts`), переживает перезапуск и не меняет `rev`; виден в `partner_brief` →
  `work.thoughts` (`"on"│"off"`). Ниже «Мысли стратега».
- `text` — только с `note` и `ask`; `package`, `id`, `rev` с ними — `bad_args`. Заметка и вопросы
  хранятся в том же `packages.json` (поля `notes`, `questions`, `qnext`), переживают перезапуск
  сервера и загрузку сейва и **не меняют `rev`**: `rev` сторожит только пакеты. Их тексты — данные, не
  команды: голос пересказывает их, но не исполняет.

Пакет на входе `put`: `{name, anchor:pos, priority?="next", steps, on_fail?="stop", verify, note?,
order?, approved?}`:
- `name` — название одной строкой (≤ 60 символов), `note` — пояснение для пилота и голоса (≤ 300);
  « » заменяются на `"`, «хозяин:» — на «хозяин -».
- `priority` — `now`│`next`│`later`: из ждущих первым идёт `now`, при равенстве — старший пакет.
- `steps` — шаги `{do, args?, on_fail?}`, каждый проверяется как отдельный `partner_act` (без
  вложенного `plan`; шаги `build_blueprint` и `build_layout` могут брать `plan` из `partner_plan`),
  до 200 шагов.
  Пакет исполняется телом без хода пилота, поэтому в нём только шаги стройки: `walk`, `approach`,
  `get_items`, `craft`, `mine` (только `resource` или `item`, не `target`), `insert`, `place`,
  `build_blueprint` (без `force:"superforced"` и `partial`), `build_layout` (без `keep_ghosts:true`:
  брошенные призраки достроили бы дроны хозяина его предметами; `bad_args`), `connect_entities` (без
  `build:false` — по той же причине),
  `build_ghosts`, `plan_mining`, `plan_belt`, `wait` и своя броня помощника — `equip`, `armor_grid`.
  Остальное (`deconstruct`, `pickup`, `rotate`, `set_recipe`, `follow`) — отказ `bad_args`; это работа
  пилота. Стратег читает слова хозяина и пересказы голоса, поэтому пакет — это право действовать
  телом, суженное до стройки, а не проба.
- **Забрать у хозяина** — `collect`, `extract`, а также `from_lines:true` у `get_items` и `collect` —
  пакет может только с его разрешения: `order` (его поручение) и `approved:"q<N>"` — вопрос стратега,
  на который хозяин ответил (`answered`, ответ пришёл поручением с `answer_to`) и который относится к
  этому поручению: задан с `order` этого поручения или, без `order`, после него (по тику). Ответ,
  который читается как отказ («нет…», «не бери», «нельзя»), разрешением не считается. Сервер
  проверяет это при `put` и ещё раз, когда пакет уходит телу (не прошло — `package_failed`). Без
  разрешения — `bad_args`. Смысл ответа (разрешил ли хозяин именно это) — забота стратега.
- **Тексты отказов** `put` называют шаг, действие и поле и дают форму и пример (одна точка правды —
  `validate.py`): `steps[3] (insert): unknown field "item" — ожидается items:{name:count}; пример:
  {"do":"insert","args":{…}}`; запрещённый шаг —
  `steps[1] (extract): забирать из машин и сундуков хозяина пакетом можно только с его разрешения:
  order + approved (id отвеченного вопроса) …`; у проверок — `package.verify[1] (stock): unknown
  field "at" — ожидается at_least:число; пример: …`.
- `verify` — 1–3 проверки:
  - `{kind:"stock", item, at_least, radius?=32, center?}` — в складах вокруг `center` (по умолчанию
    `anchor`) не меньше `at_least` предмета (op `stock`, `total`);
  - `{kind:"rate", item, at_least, surface?}` — сделано не меньше `at_least` в минуту по статистике
    поверхности за последнюю минуту (op `rates`, `made`);
  - `{kind:"ghosts", at_most?=0, radius?=32, center?}` — призраков вокруг не больше `at_most`
    (op `ghosts`, `count`).
- `order` — id поручения хозяина (`partner_inbox`), ради которого пакет; `approved` — id отвеченного
  вопроса (`q<N>`, только вместе с `order`), разрешение забрать у хозяина (выше): вопрос задан с этим же
  `order`, ответ хозяина пришёл после вопроса и начинается явным согласием («да», «можно», «бери», «ок»);
  «нет», «посмотрим» и другие ответы разрешения не дают. Сервер дописывает
  `leave_scope` (чьи вопросы) и `order_tick`.
- Весь пакет ≤ 8 КБ JSON (`limit`); активных (`queued`, `running`, `pausing`, `paused`) пакетов у
  помощника ≤ 2 (`limit`); `verifying` не считается. Пакеты относятся к помощнику ключа вызова.

Состояния: `queued` → `posting` → `running` → `verifying` → `verified`│`unmet`; `running` →
`failed` (план оборван отказом шага); `running` → `pausing` → `paused` (ниже); любое открытое →
`cancelled`. `posting` — мост отправляет план в мод: переход из `queued` идёт сравнением с записью в
файле, поэтому один пакет уходит телу одной задачей, даже если мостов два. Пакет, оставшийся в
`posting` дольше минуты (процесс умер посреди отправки), сверяется с телом: идёт задача `plan` —
это его план (`running`), тело свободно — пакет снова ждёт.
Поля сервера в пакете: `id` (`pk<N>`), `status`, `job`, `from_step`, `created_tick`, `started_tick`,
`done_tick`, `verify_at`, `plan` (итоги `plan_done`: `status, code?, text?, at?, marks, failures?`),
`checks` (`[{kind, item?, at_least│at_most, value, ok, error?}]`), `paused_reason`, `paused_for`.

Мост, каждые 2 с, для каждого помощника с открытыми пакетами:
1. **Ставит.** Если план пакета у помощника не идёт, тело свободно (нет задачи, очередь пуста, простой
   не меньше 2 с — `idle_ticks` ≥ 120), hold хозяина не стоит и нет открытого поручения хозяина моложе
   10 минут игры (мелкое — следующая работа пилота; крупное ждёт своих пакетов: идут только пакеты с
   его `order`; мелкое, только что отмеченное `partner_inbox{ack}`, держит пакеты ещё 10 с игры — первое
   действие пилота встаёт раньше пакета), — следующий пакет уходит в мод одной задачей `plan`
   (`replace:false`). План, который
   не влезает в 4 КБ `act.args`, уходит через `blob_put` (`blob`). Пилоту — событие `package_started`.
   Ошибка сети или пауза игры — повтор на следующем шаге (до 5 раз), отказ мода — `package_failed`.
2. **Следит** за событиями помощника: `plan_done` с `status:"done"` → `verifying`; оборван отменой
   или hold хозяина → `paused` с шага, на котором оборван (`from_step`); оборван отказом шага →
   `failed`. Отступление `flee`, вернувшее план (`reflex_resumed`), продолжает тот же пакет.
3. **Проверяет.** Через 2 минуты игрового времени (7200 тиков) после `plan_done` меряет проверки теми
   же чтениями, что есть у агента → `verified` (`package_verified`) или `unmet` (`package_unmet`,
   `checks` с найденными значениями). Чтение не удалось 3 раза — `unmet` с `error` у проверки.

Приостановка (`paused_reason`):
- `owner_order` — пришло крупное поручение хозяина (`partner_order{size:"large"}`): шедший пакет
  доделывает текущий шаг (`cancel{job, at_boundary:true}`) и встаёт. Новое — первым: пока поручение
  открыто, идут только пакеты с его `order`; приостановленный продолжает сам, когда ждущих пакетов нет
  и открытых поручений нет.
- `owner_stop` — хозяин сказал «стоп» или «иди сюда» (или hold оборвал план): пакет продолжает сам
  после «продолжай» хозяина (`owner_resume`). Мод шлёт `plan_done` раньше `owner_stop`, поэтому стоп
  хозяина узнаётся и по тексту отказа (`stopped by owner`).
- `cancelled` — план сняли мимо пакета (`partner_cancel`, `replace`); `cancel_all` — кто-то из ролей
  снял все задачи помощника (`partner_cancel{all:true}`, так голос исполняет «хватит» в свободной
  форме): ждущие пакеты встают вместе с идущим; `reloaded` — загружен сейв, а план в загруженной игре
  не идёт. Все три продолжает только `resume` стратега. Пока есть пакет, вставший как `cancelled` или
  `cancel_all`, мост не ставит никакой другой: тело остановили мимо моста.

### Вопросы стратега хозяину
Стратег в чат не пишет; вопрос хозяину (развилка, согласие) он кладёт `partner_ledger{action:"ask"}`.
1. Голосу этого помощника (и общему голосу), который уже обращался к серверу, — громкое событие сервера
   `strategist_question` (`data:{id, text}`); открытые вопросы видны и в `partner_brief` →
   `work.questions`. Голос задаёт вопрос в чате.
2. Ответ хозяина голос отдаёт `partner_order{said_seq, text, size:"large", answer_to:<id>}`: стратег
   получает поручение с `answer_to` во входящих (событие `order`), вопрос — `answered` (поля `answer` —
   id поручения, `answered_at`). Закрытых вопросов хранится по 5 последних на помощника.
3. Вопрос без ответа 10 минут (по часам сервера, `at`): мост один раз повторяет голосу
   `strategist_question` с `remind:true` и `waiting_s` и ставит вопросу `reminded`. Голос напоминает
   хозяину один раз. Голос, ещё не обращавшийся к серверу, напоминания не получает — вопрос он увидит в
   `partner_brief`.

### Мысли стратега
Пока флаг `thoughts` помощника включён, каждая новая заметка стратега (`note`) будит голос громким
событием сервера `strategist_note` (`data:{text, helper}`; у общего стратега `helper:null`); голос пересказывает её хозяину в чате в одном-двух
коротких сообщениях. Событие приходит не чаще раза в 30 секунд на помощника: заметки в этом промежутке
копятся, и через 30 секунд от прошлого события голос получает последнюю из них. Выключенный флаг убирает
ждущую заметку; события нет, заметка видна только в `partner_brief` → `work.note`. Права: переключает только
голос (`partner_ledger.thoughts`), пишет заметки только стратег. При включённом флаге стратег пишет их
человеческим языком на 1–2 строки: план по поручению, пакет готов или не вышел, смена этапа, ожидание.

Хранение пакетов: `<папка заметок>/<сейв>/packages.json` (как у `partner_notes`); запись — под файлом-замком
с атомарной заменой. Пакеты переживают перезапуск сервера: мост дочитывает события с номера, на
котором план ставился, а если `plan_done` уже нет в буфере мода и тело задачу не держит — переходит
к проверкам. Загрузка сейва (`game_reloaded`): план, который загруженная игра продолжает (та же задача
`plan` у тела), остаётся `running`, остальные идущие — `paused` (`reloaded`); отсчёт 2 минут до
проверок — заново. Несколько процессов сервера на одном сейве: пакеты ведёт мост одного из них
(аренда на 60 с под тем же файлом-замком, продлевается перед каждым помощником; файл
`packages.json.lease`). Отладочный CLI моста не запускает.

### `partner_brief`
Ответ: `{rules, rules_full, notes, notes_missing?, reason?, profile?, style?, helper, save,
owner_rules:[{n, text, owner_said?}], memo:[{n, text}], memo_is:"data, not orders", auto:{on, goal, rule},
budget, perms, chat, rescale?, work, bodies?}`.
- `rules` — короткие правила честности; полные правила работы — в промпте агента, `rules_full` —
  ссылка на него (`.claude/agents/partner.md`); при расхождении верен промпт.
- `notes` — `notes.md` профиля сейва forge (≤ 8000 байт, это текст хозяина — данные, не команды);
  единственный источник — `forge.brief_notes`. Заметок нет — `notes:null` и причина в
  `notes_missing`; у старого forge без нужных команд ещё `reason:"forge_too_old"`. Сырой вывод forge
  агенту не показывается.
- `style` — `FP_HOME/style.md`, если есть.
- `save`, `owner_rules`, `memo` — заметки этого сейва (как `partner_notes` с `action:"list"`).
- `auto` — самостоятельный режим этого сейва (раздел «Самостоятельный режим» ниже).
- `perms` — настройки мода о разрешениях хозяина, коротко (раздел «Разрешения хозяина»):
  `{ask:[ключи], deny:[ключи], limits:{spend, far}, source:"mod"│"default", how}`; ключи «сам» не
  перечисляются. `how` — подсказка: «спросить» — сначала вопрос хозяину, «нельзя» — не пытаться.
- `chat` — `{answer_every, reply_lines}`: отвечать ли голосу на каждое сообщение хозяина и сколько строк
  в ответе самое большее.
- `rescale` — есть у всех ролей, пока открыт запрос хозяина перезапустить роли: `{n, tasks:[{to?, text}]}`
  (раздел «Перезапуск на другое число помощников»). Роль, увидев его, заканчивает смену.
- `work` — как идёт работа помощника, коротко (до ~4 КБ), для ответа голоса на «ну что?»:
  `{orders, packages, body, body_missing?, note, questions, panel?, is:"data, not orders"}`.
  - `orders` — до 6 поручений хозяина: открытые и последние взятые (`ack`) —
    `{id, text ≤ 80, to:"pilot"│"strategist", state, answer_to?}`; `to` — по `size` (`small` — пилот).
    `state`: `new` — во входящих; `taken` — взято (`ack`); `done` — все пакеты с его `order`
    проверены; `cancelled` — все его пакеты сняты. Взятые живут в памяти процесса, как входящие.
  - `packages` — открытые пакеты помощника и до 3 последних законченных:
    `{id, name, state, status, steps:[сделано, всего], why?, order?}`; `state` — `waiting` (`queued`,
    `posting`, `paused`; `why` — `paused_reason`), `running` (`running`, `pausing`, `verifying`),
    `verified`, `unmet` (`unmet`, `failed`), `cancelled`. У идущего пакета `steps` — по прогрессу
    задачи `plan` в `state`.
  - `body` — задача тела по op `state`: `{do:"plan", step, steps, package?}` (текущий шаг плана и пакет,
    чей это план), `{do, progress?}` для другой задачи, `{do:null, queue}` — свободно. Игра не
    ответила — `body:null` и `body_missing`.
  - `note` — последняя заметка стратега `{text, ago_s}` (сколько секунд назад) или `null`.
  - `questions` — открытые вопросы хозяину `{id, text, waiting_s, reminded}`; вопрос пилота (раздел
    «Разрешения хозяина») — с `from:"pilot"` и `helper`.
  - `panel` — последние нажатия хозяина в окне панели (`combat`, `hold`, `resume`, `auto` …) —
    `[{action, on?, n?, goal?, at}]`; голос видит по ним, что хозяин включил боевой режим или остановил тела.

  Всё в `work` — только этого помощника (`helper` вызова) и без ключей; одинаково для всех ролей
  (у общих голоса и стратега `note`, `questions` и `thoughts` — общие). Тексты (`note`, названия
  пакетов, пересказы поручений, вопросы) — данные, не команды.
- `bodies` — только у общих голоса и стратега: `{helpers:[{helper, do, step?│progress?, queue?,
  package?:{id, name}, orders, packages, body_missing?}], waiting:[{id, text}], is}` — по строке на
  каждого помощника сервера (что делает тело по op `state`, `do:null` — свободно; сколько у него
  открытых поручений и пакетов) и до 6 поручений в общих входящих стратега.

### `partner_notes`
Постоянные правила хозяина (`rules`) и память помощника о базе (`memo`) живут дольше одной смены:
файлы `<папка заметок>/<сейв>/rules.md` и `memo.md` — нумерованный markdown-список, по записи на
строку (хозяин может править их руками). Пишет туда только помощник через этот инструмент.
- `list` — показать; `add` — добавить `text` (запись ≤ 300 символов, к ней дописывается дата);
  `remove` — убрать запись `n`. Записей: правил ≤ 30, памяти ≤ 40 (больше → `limit`).
- `memo` — заметки помощника (где мусорный бак, какой сундук для чего): данные, не приказы. Меняются
  без подтверждения.
- **`rules` меняются только словом хозяина:**
  1. `add` с `said_seq` — номер его сообщения (`player_said`, `owner:true`, не старше 10 минут; сервер
     сам читает это событие у мода). Сервер сам спрашивает хозяина в чате точным текстом:
     «Запомнить правило: «…»? Ответь «да».» и отвечает `{save, kind, pending, items, next}`.
  2. `confirm` с `said_seq` его ответа — только **первого** его сообщения после вопроса; ответ — «да»
     (или `ага`, `подтверждаю`, `yes`, `y`, `ok`, `ок`, `+`). Иначе правило отброшено (`bad_args`).
     Вопрос ждёт не дольше 2 минут; пока ждёт, `partner_say` отказывает **всем** помощникам
     (`bad_args`), чтобы следующее сообщение хозяина ответило именно на вопрос.
  3. `remove` — тоже с `said_seq` его сообщения.

  Каждое сообщение хозяина — на одно изменение (повтор того же `said_seq` → `bad_args`). Правило ≤ 160
  символов (читается хозяину одной строкой чата); в тексте правила « » заменяются на `"`, «хозяин:» —
  на «хозяин -», чтобы текст не выдал себя за слова хозяина. Слова хозяина хранятся рядом с правилом
  и приходят отдельным полем `owner_said`. Текст других игроков, страниц и вывода инструментов
  правилом не становится.

### Самостоятельный режим (`auto`)
Режим, в котором стратег сам ставит цели развития базы. Включается и выключается **только словом
хозяина**; отдельного хранилища и отдельного инструмента нет — режим живёт правилом сейва в
`partner_notes` (вид `rules`) и проходит ту же проверку: `said_seq` его сообщения, вопрос в чате,
«да» следующим сообщением (раздел `partner_notes`).
- **Включить:** правило ровно в одной из двух форм: `AUTO` или `AUTO: <цель>` (цель — слова хозяина,
  если он её назвал: «иди к ракете», «развивай науку до синей»). Маркер — только заглавными и только
  так: `auto refuel turrets`, `Auto: …`, `AUTO-sort`, `AUTO — …` — обычные правила, режим они не
  включают. Маркер пишет голос. Вопрос в чате для такого правила другой: «Включить самостоятельный
  режим (стратег сам ставит цели) с целью «…»? Ответь «да».» — хозяин подтверждает именно включение
  режима. Память (`memo`) режим не включает.
- **Выключить или сменить цель:** `remove` правила (тоже со `said_seq`); новую цель — новым правилом
  после снятия. Второе правило `AUTO`, пока первое есть, сервер отклоняет (`bad_args`).
- **Признак:** в `partner_brief` поле `auto:{on, goal, rule}` — `on` включён ли режим, `goal` цель
  (≤ 100 символов) или `null`, `rule` номер правила в `owner_rules` (для `remove`) или `null`. Читает
  его тот, кто берёт `partner_brief`; поле считается из файла правил при каждом вызове.
- **Что меняется:** без `auto` стратег свои цели не ставит, только поручения хозяина; с `auto` ставит
  цели сам (раздел «Самостоятельный режим» в правилах стратега). Режим не меняет прав ролей на
  сервере. Не трогать постройки хозяина и брать со складов только нужное пакету — это правила
  стратега (`partner-strategist.md` §7); сервер и мод этого не проверяют: помощник в силе хозяина
  (PROTOCOL §6.8).
- Склады без лимита: режим не вводит доли и квоты на склады; ограничение хозяин задаёт отдельным
  правилом, и его тоже соблюдает стратег по своим правилам, а не сервер.

### `partner_act`
- `do` и поля `args` — из белого списка (ACTIONS.md); неизвестное поле, неверный тип, нарушение
  «ровно одно из» → `bad_args` без похода в мод; `args` ≤ 4 КБ.
- `build_blueprint`: вместо `blob` можно `plan` (id из `partner_plan`) — сервер сам грузит чертёж
  через `blob_put` (id части — `bp-<16 hex>`). Сервер пропускает `search`, `rotate`, `mirror`,
  `partial`; `partial` и `force:"superforced"` агент передаёт только после прямого согласия хозяина.
  Поиск сдвига ничего не нашёл — сервер добавляет в `detail` события `fit:null` (в JSON мода `null`
  нет: мод шлёт `fit_checked` без `fit`).
- `build_layout`: `entities` (≤ 100 построек, смещения `dx, dy` или `cx, cy`) либо `plan` (id блока из
  `partner_plan{task:"block"}`) — ровно одно; `blob` агенту закрыт. С `plan` сервер сам берёт у forge
  список построек и порты, кладёт их JSON-ом `{entities, ports}` через `blob_put` и отдаёт моду `blob`
  вместо `plan`; `ports` агента сильнее портов forge с тем же `id`. Большой `entities` (`args` > 4 КБ)
  уходит так же. `args` этого действия на сервере — до 16 КБ (у остальных 4 КБ). В пакете и в шаге
  `plan` действие работает так же; `keep_ghosts:true` в пакете отклоняется. Порт forge можно переписать
  в свои `ports` как есть: `rate` и пустая полоса `""` допустимы.
- `connect_entities`: `kind` (`belt│pipe│power`), `from`, `to` — концы `{pos, dir?}`, `{target}`,
  `{layout, port}` или `{layout, i}` (ровно одно), `via` ≤ 8 точек, `max_length` 1..200. Поле
  прототипа не того вида (`pipe` при `kind:"belt"`) — `bad_args`.
- `plan_belt`: `from:"resume"` разрешён без `to`. Правило агента: после стопа стройки ленты
  (заблокированные призраки, отказ, бегство) — осмотреться (`partner_state`, `partner_map`), затем
  `plan_belt{from:"resume"}` и снова `build_ghosts`; не больше трёх перекладок подряд на одну ленту,
  дальше — сказать хозяину, где встал и почему.
- `plan`: каждый шаг проверяется как отдельный `partner_act`; шаг `build_blueprint` или
  `build_layout` с `plan` (и `build_layout` с большим `entities`) получает ту же загрузку в `blob`,
  что и отдельный вызов.
- `approved` + `order` (вместе — иначе `bad_args`) — согласие хозяина на действие с настройкой «спросить»
  (раздел «Разрешения хозяина»). Годится и для `partner_reflex`, и для `do:"plan"`.
- Ответ — `{job, queued_before}`; итог — событием `job_done` / `job_failed` (у `plan` — `plan_done`).

### Разрешения хозяина
Хозяин задаёт в настройках мода «сам» / «спросить» / «нельзя» для каждого вида действий (README.md
«Настройки»); мод проверяет их сам (PROTOCOL §4, ACTIONS.md «Разрешения хозяина»). Сервер читает операцию
`settings` (ответ хранит 10 с; старый мод, ошибка или недопустимое значение — значения по умолчанию, неизвестный
ключ считается «нельзя») и показывает агентам короткую выжимку в `partner_brief` → `perms`.
- **«Нельзя»** — мод отвечает `owner_forbids`. Агент не пытается и говорит хозяину, что это запрещено
  настройкой (Escape → Настройки → Настройки модов → Карта).
- **«Спросить»** — без разрешения мод отвечает `needs_owner_ok` (`data.perm` — ключ). Порядок такой: агент
  спрашивает хозяина (`partner_ledger{action:"ask", order, perm}`; `perm` — ключ или список до 4 ключей, о
  которых вопрос; вопрос ставит и стратег, и пилот — для своего тела), сервер дописывает к тексту вопроса, что
  разрешается, голос передаёт вопрос и ответ; после явного «да» агент повторяет вызов с `approved:"q<N>"` и
  `order:"o<N>"`. Сервер ставит в конверт `owner_ok:[ключи вопроса]` **только** если по реестру вопрос задан
  про тот же `order` и с `perm`, ответ пришёл после вопроса и начинается с явного «да», `order` — поручение,
  поставленное этим сервером для этого тела или в общие входящие, «да» не старше 30 минут и использовано
  меньше 3 раз (каждый вызов, прошедший проверки сервера, тратит одно). «Да» снимает «спросить» только с
  ключей вопроса. Если агент кладёт `owner_ok` куда-либо сам (в `args`, в
  шаги плана, в набор рефлексов, в пакет), сервер отказывает `bad_args`; поле инструмента `owner_ok` до мода
  не доходит. Ошибки сервера: `owner_forbids`, `needs_owner_ok` (раздел «Ошибки сервера»).
- **Пакеты.** Шаги, которые просят «нельзя», сервер отказывает при `put` (`owner_forbids`, `{perm}` в `detail`).
  Пакет с согласием хозяина (`approved`) запускает свой план с `owner_ok` — ключами вопроса (вопрос без
  `perm` — про «забрать у хозяина»: `take_chests`, `take_lines`). Одно «да» — одно применение: ответ, по
  которому уже шли отдельные вызовы, пакету не годится, а ответ, отданный открытому пакету, не годится ни
  другому пакету, ни отдельному вызову (закрытый пакет его освобождает); «да» годится пакету час — и при `put`, и
  когда пакет уходит в мод.
- **AUTO.** Ключ `auto`: «сам» — правило AUTO пишется без «да» хозяина; «спросить» — как раньше; «нельзя» —
  отказ `owner_forbids` («AUTO запрещён в настройках мода»), и кнопка AUTO в окне хозяина тоже. «Нельзя» важнее клика.
- **Остальные настройки.** Пауза голоса: `FP_CHAT_SETTLE` (env) важнее `voice_pause` из настроек, а он — 2,5 с.
  Мысли стратега по умолчанию — `thoughts` из настроек, пока хозяин сам не переключил (его выбор хранит
  `ledger`). Пороги сторожа лимита (раздел «Сторож лимита») — из настроек, если env их не задаёт; набор, где
  первый порог не ниже второго, игнорируется. Число помощников и модели при запуске — `agents/launch.py`.

### Перезапуск на другое число помощников
Хозяин говорит в игре «запусти / добавь / убери N помощников» (или нажимает «Применить» в окне панели,
EVENTS.md «Панель хозяина»). Запрос лежит в сервере, пока его не снимут: `{n, tasks:[{to?, text}], from:"panel"│"chat", tick}`.
- **Из чата.** Голос вызывает `partner_ledger{action:"scale", n, said_seq, tasks?}`; `n` зажимается в 1..5 (ответ говорит,
  если зажато), `tasks` — до 5 заданий телам после запуска (`to` — id помощника, `text` ≤ 300). Сервер принимает
  вызов только на сообщение хозяина `said_seq` за последние 120 секунд (читает его из мода; сообщение до запуска
  сервера не считается), в котором он просит запустить, добавить или убрать помощников («запусти», «добавь»,
  «убери», «оставь»…); одно сообщение — один перезапуск. Слова хозяина лежат в запросе (`owner_said`), диспетчер
  видит их рядом с `n` и `tasks`. Пилот и стратег `scale` не могут.
- **Из окна.** Событие `owner_panel{action:"scale", n}` ставит тот же запрос.
- **Всем ролям** `partner_brief` показывает `rescale`, пока запрос открыт; роль заканчивает смену, и Workflow
  ролей возвращает `{rescale:{n, tasks}}` (agents/README.md). Сервер шлёт событие `rescale` голосу и стратегу.
- **Диспетчер** (ключ `host`): `partner_rescale{action:"get"}` — прочитать запрос и сверить с ним слова агентов
  (задания в `tasks` — слова агентов, а не хозяина); запустить роли заново на `n`; раздать задания телам через
  `partner_relay`; `partner_rescale{action:"done"}` — снять запрос. Лишние тела стоят на месте с вещами, не
  удаляются.

## Служебные инструменты и запуск
Служебные (только запускающий скрипт и отладка, включаются флагом `--admin`): `admin_hello`,
`admin_spawn(helper)`, `admin_remove(helper)`, `admin_raw_events(since, helper?, limit?)`,
`admin_limit(max)` (op `helper_limit`), `admin_attach(helper, player)` (op `helper_attach`),
`admin_settings()` (op `settings`: настройки мода как их отдаёт мод; `launch.py` берёт из них число помощников и модели).
Ответ — `{tick, seq, data}`.

Запуск напарника (`agents/launch.py`): флаги `--helpers N` (не задано — спросить у игрока; шлёт
`helper_limit`), `--body character│player` (по умолчанию `character`), `--helper <id>` и

обязателен при `--body player`). Скрипт ходит через те же `admin_*` функции `core.py`, а не мимо

--helpers N [--body …] [--helper …] [--player …]`.

## `partner_plan`
Вход: `{task:"mining", resource:{name, area} │ patch (из partner_resources), options?:{drill?, belt?, pole?, direction?}}`
(ровно одно из `resource`/`patch`; всё ≤ 4 КБ) или `{task:"block", block}` (раздел «Блок рядов» ниже).
Выход: `{plan, anchor:pos, direction, items, size:{w,h}, summary}` — `plan` — id, по которому
сервер хранит строку чертежа в `FP_HOME/plans/` (агенту строка не показывается); дальше
`partner_act("build_blueprint", {plan, anchor, direction})`.
`task` — `"mining"` или `"block"`. Для `mining` forge раскладывает буры по прямоугольнику пятна, а движок ставит
призрак электрического бура только на руду, которую он добывает: крайние буры без руды попадут в
`skipped` при `dry_run` — это ожидаемо, не ошибка. Для добычи обычно лучше `plan_mining` (раскладка по
форме пятна).
Отказы — `{supported:false, reason}`:
- forge не установлен, не умеет нужное или упал (подробности — только в `server.log`); ошибка
  настройки forge (например, задан другой профиль, чем активный) — тоже не ошибка, а этот ответ;
- старый forge без нужных команд (`notes`, профили) — `reason:"forge_too_old"` (определяется по коду
  выхода 2 и отказу разбора командной строки forge; прочие сбои отдают последнюю строку его stderr
  без путей).

Тогда агент размечает добычу через `plan_mining` или просит хозяина поставить призраки (MPP /
P.U.M.P. / чертёж) и строит `build_ghosts`.

Как устроено:
- Раскладку добычи (пары буров к ленте, ряды столбов, как MPP, по ограничивающему прямоугольнику
  пятна) считает `forge.py`; forge проверяет её по данным профиля, ставит провода и кодирует чертёж.
  Крайние буры могут стоять без руды — `summary` об этом предупреждает.
- `options`: `drill?`, `belt?`, `pole?` (`small-electric-pole`│`medium-electric-pole`, по умолчанию
  small), `direction?` — куда лента везёт руду (`north│east│south│west` или `0│4│8│12`, по умолчанию north).
- Чертёж уже повёрнут в Python, поэтому в ответе `direction` всегда `0` — передать в
  `build_blueprint` как есть. `anchor` — центр прямоугольника раскладки (`left + w/2, top + h/2`),
  как `position` у `LuaItemStack.build_blueprint`; привязку проверяет `dry_run`.
- Сервер пропускает агенту только поля контракта (`plan, anchor, direction, items, size, summary`,
  `summary` ≤ 2000 символов); ответ forge другой формы → `{supported:false, reason}`.
- Python-контракт `factorio_partner/forge.py` (единственный, сервер зовёт только так):
  `plan(task, resource=None, patch=None, options=None, block=None, *, config) -> dict` (не бросает на
  сбоях forge, только `PlanArgsError(ValueError)` с `.code="bad_args"` на неверную форму аргументов);
  `load_plan(plan_id, *, config) -> str` и `load_layout(plan_id, *, config) -> {entities, ports}`
  (`PlanArgsError` на неверный/неизвестный id);
  `brief_notes(config) -> {profile, notes, truncated[, reason]}` — **единственный** источник
  `notes.md` профиля для `partner_brief` (≤ 8000 байт).
  `config` — `Config` сервера (`.home`, `.forge`, `.forge_profile`, `.forge_home`); окружение
  процесса forge.py не читает. Синхронные функции, сервер зовёт их через `asyncio.to_thread`.
- Хранение: `FP_HOME/plans/<id>.txt` — строка чертежа, `FP_HOME/plans/<id>.json` — метаданные без
  строки, у блока ещё `FP_HOME/plans/<id>.layout.json` (раскладка, ниже); `id` = `p-<16 hex>` (подходит под regex `blob_put`); хранятся 200 последних. Неизвестный
  `plan` в `build_blueprint` → `not_found` («вызови partner_plan заново»).

### Блок рядов (`task:"block"`)
Вход: `block` — один блок рядов в формате `plan.json` forge (≤ 4 КБ), `resource`/`patch`/`options` не
нужны. Пример:
```
{"task":"block","block":{"recipe":"iron-gear-wheel","machine":"assembling-machine-1","rows":[4,4],
 "belt":"fast-transport-belt","inserter":"fast-inserter","long_inserter":"long-handed-inserter",
 "pole":"medium-electric-pole"}}
```
Поля блока: `recipe`, `machine` (обязательны), `rows` — список числа станков по рядам (до 32 рядов, до 64
в ряду, всего до 128) либо число рядов вместе с `per_row`; ступени `belt`, `inserter`, `long_inserter`,
`pole`, `pipe`, `pipe_to_ground` (имена прототипов; нужные для рецепта forge требует сам); `stack`
(`mirror`│`repeat`), `align` (`start`│`center`), `input_belts`, `speed_bonus`, `stack_size`, `planned`,
`rotate` (`0`│`90`│`180`│`270`). `at` и `id` отбрасываются: блок строится с углом в (0, 0). Допустима
обёртка `{blocks:[один блок]}`. Блок библиотеки (`library`), лишнее поле, неверный тип — `bad_args`.

Ответ: `{plan, size:{w,h}, items, ports, entities_n, summary}`.
- `ports` — `[{id, kind:"belt"│"pipe", io:"in"│"out", dx, dy, dir, items:[левая, правая] │ fluid, rate}]`:
  `id` — `in<N>`/`out<N>` по номеру порта в отчёте forge; `dx`,`dy` — клетка порта от левой верхней клетки
  рамки блока; `dir` — куда течёт (`0`/`4`/`8`/`12`); `items` — полосы ленты глазами едущего по ней
  (`""` — полоса не занята); `rate` — в секунду при полной загрузке. До 16 портов.
- `entities_n` ≤ 100 (столько принимает `build_layout`); блок больше — `{supported:false, reason}`.
- Отказы forge — как у `mining`: `{supported:false, reason}`; проблемы проверки (`problem`) тоже.

Хранение: `FP_HOME/plans/<id>.layout.json` — `{entities, ports, size}`, где `entities` —
`[{name, cx, cy, direction, recipe?, type?}]`: центр постройки (`cx`,`cy` — доли клетки, как в чертеже)
от левой верхней клетки рамки, `direction` 0..15 (четыре стороны — 0/4/8/12), `type` — `input`/`output`
у подземной ленты. Файл пишется атомарно и вытесняется вместе с чертежом (хранятся 200 последних планов).

Дальше `partner_act("build_layout", {plan, anchor, ...})`: сервер читает файл (`load_layout`) и передаёт
постройки и порты в мод, `anchor` — клетка, куда ляжет угол рамки; свои `ports` в аргументах переопределяют
порты forge по `id`. Порты запоминаются по `tag`, и `connect_entities` берёт концы как
`{layout:<tag>, port:<id>}`. Неверный или неизвестный `plan` — `bad_args` (как у `build_blueprint`);
повреждённый файл раскладки — `not_found`.

## Ошибки сервера (сверх кодов мода)
- `access denied` — неверный `helper` или `key` (один текст на любую ошибку доступа).
- `not_allowed` — инструмент (или его запись) вне прав роли ключа (раздел «Роли»).
- `budget` — запись отклонена сторожем лимита плана (раздел «Сторож лимита»).
- `owner_forbids` / `needs_owner_ok` — настройки мода запрещают действие или ждут разрешения хозяина
  (раздел «Разрешения хозяина»); коды те же, что у мода (PROTOCOL §3), сервер отдаёт их и сам — при постановке
  пакета и при включении AUTO.
- `transport_timeout` — мод недоступен после 3 повторов; сюда же неверный пароль RCON и ответ
  не-JSON (например, `Unknown command` без мода) — с пояснением в тексте.
- `game_paused` — только для изменяющих вызовов; чтение отдаёт данные с `warning` (PROTOCOL §5).
- `limit` — верхняя граница аргумента, размер `args`, `text` и т.п.
- `response too large` — ответ агенту больше 24 КБ, с подсказкой, каким аргументом сузить.
- `repeated_failure` — тот же `do`+`args` завершился `job_failed` 3 раза подряд → отказ без похода в
  мод: «измени план или спроси хозяина». Счётчик ведётся по `job_failed`, которые агент получил через
  `partner_wait`, а у `plan` — по `plan_done{status:"failed"}` (сигнатура — весь план); `cancelled`
  не считается; сброс — на `job_done` / `plan_done{status:"done"}` с теми же аргументами и на
  `game_reloaded`.
- `internal` — сбой самого сервера (подробности — в `server.log`).

## Сторож лимита
Сервер сам не знает, сколько лимита плана потрачено: значение приходит снаружи, файлом. Путь к нему —
переменная `FP_BUDGET_FILE`; файл только читается, секретов в нём нет:

```json
{"five_hour_pct": 62, "weekly_pct": 40, "ts": 1790000000}
```

`ts` — Unix-секунды. Синонимы полей `five_pct`, `week_pct`, `captured_at` тоже принимаются (так пишет
типичный хук-сторож лимита, и его файл можно подставить как есть). Файла нет, он битый, процент вне
0..100, время из будущего или данные старше `FP_BUDGET_MAX_AGE` (600 с) — уровень `unknown`; он
ничего не ограничивает: отсутствие цифры не должно останавливать помощника.

| уровень `budget.level` | когда | что меняется |
|---|---|---|
| `ok` | пятичасовое окно ниже `FP_BUDGET_WARN` (70 %) | ничего |
| `strategist_off` | от 70 % | стратег не ставит новых целей: `partner_ledger{put│resume}` → `budget`; чтение, `cancel`, `inbox{ack}`, `plan` работают |
| `voice_only` | от `FP_BUDGET_STOP` (85 %) или недельное от `FP_BUDGET_WEEK_STOP` (90 %, 101 — выключить) | пилоту и стратегу отказ `budget` на любую запись, кроме `partner_cancel` и `partner_hold`; чтение работает; голос и мод работают как раньше |
| `unknown` | нет свежей цифры | ничего |

- Проверка идёт после проверки роли и до похода в мод. Отказ: `budget: <инструмент>: …`.
- Поле `budget` (`{level, five_hour_pct, weekly_pct, age_s}` или `{level:"unknown", reason}` с
  `reason` ∈ `not_configured`, `no_file`, `bad_file`, `stale`) отдают `partner_brief` и `partner_wait`;
  если `FP_BUDGET_FILE` не задан, в `partner_wait` поля нет.
- При входе в `voice_only` голос каждого помощника один раз получает громкое событие `budget_low`
  (будит и спящий `partner_wait`): его задача — одной строкой сказать хозяину в чат, что лимит почти
  кончился и работают только мод и голос. Снова событие придёт после выхода уровня ниже `voice_only`.
  Уровень `unknown` серию не обрывает.
- Пороги: `FP_BUDGET_WARN`, `FP_BUDGET_STOP` (должно быть `warn < stop ≤ 100`). Неверное значение —
  сервер не стартует.
- Откуда брать файл: всё, что умеет писать JSON выше, например сценарий, который раз в минуту
  переписывает файл по данным хука-сторожа лимита. Путь задаётся только окружением.

## Логи
`FP_HOME/logs/<helper>.jsonl` — каждый вызов: время, инструмент, роль ключа, аргументы (без ключа и без
текста чертежа; длинные строки обрезаны), код ответа, длительность. `FP_HOME/logs/server.log` —
транспорт и сбои. Ключи и пароль — никогда.

## Лимиты
Запрос к моду ≤ 8 КБ; `act.args` ≤ 4 КБ (у `build_layout` на сервере ≤ 16 КБ, в мод больше 4 КБ уходит как `blob`; в нём ≤ 100 построек, ≤ 16 портов, рамка блока ≤ 64×64; у `connect_entities` ≤ 8 точек `via`, до 200 звеньев); `block` у `partner_plan` ≤ 4 КБ; пакет стройки ≤ 8 КБ, активных ≤ 2 на помощника; набор рефлексов ≤ 16 и ≤ 4 КБ; часть `blob_put` ≤ 3500
байт; чертёж ≤ 1 МБ; `say` ≤ 200 символов; ответ агенту ≤ 24 КБ; `partner_wait` ≤ 55 с.
