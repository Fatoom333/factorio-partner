# Сквозные сценарии и финал с игроком (поток K)

Здесь — как проверить поручение целиком: «поставь добычу на этой руде». Контракты — в остальных
файлах `docs/`; стенд — [TESTING.md §3–4](TESTING.md) и `tools/pc/README.md`. Этот файл ведёт поток K.

Четыре сценария. Все идут на сервере без окна, на **копии** сейва `Vulkan-Start-test`, и шлют в игру
только `/partner <JSON>`.

| Сценарий | Через что | Что доказывает |
|---|---|---|
| `e2e_mcp` | настоящий пакет сервера | MCP-сервер работает с настоящим модом |
| `e2e_ghosts` | конверты напрямую | призраки уже стоят (рамка игрока) → помощник собирает предметы и строит |
| `e2e_mining` | конверты напрямую | помощник сам размечает руду (`plan_mining`), собирает и строит |
| `e2e_forge` | настоящий пакет сервера + настоящий forge | чертёж из `partner_plan` → привязка к месту → стройка |

## Подготовка ПК (один раз)

1. Обычный стенд — как в `tools/pc/README.md` (Python для `live_client.py`, пути в `tools/pc/pc.local.json`).
2. **Python для пакета сервера.** Сценариям `e2e_mcp` и `e2e_forge` нужен Python 3.11+ с одной
   зависимостью сервера. Ставится в отдельную папку, в систему ничего не попадает:
   ```powershell
   py -3.12 -m venv D:\Temp\fp-server\venv
   D:\Temp\fp-server\venv\Scripts\python -m pip install "factorio-rcon-py[async]>=2.1,<3"
   ```
   Другой путь — ключ `server_python` в `tools/pc/pc.local.json`.
3. **forge** (только для `e2e_forge`). Пути к нему личные, в git их нет. Два способа:
   - в `tools/pc/pc.local.json`: `forge` — папка checkout'а `factorio-forge` с его `.venv`,
     `forge_home` — дом forge с профилями (если не стандартный), `forge_profile` — профиль сейва;
   - или переменными окружения при запуске: `FP_FORGE`, `FACTORIO_FORGE_HOME`, `FP_FORGE_PROFILE`
     (те же, что читает сам сервер, [MCP.md](MCP.md)).

   Если задан только `forge_home` и в этой папке лежит `.venv`, стенд понимает её как checkout.
   Сервер **не активирует** профиль forge: в forge должен быть активен профиль этого сейва, иначе
   `partner_plan` честно отвечает `supported: false`.

## Запуск

С ноутбука, из PowerShell (не из Git Bash). Слот — любой свободный 0..9.

```powershell
powershell -File tools/pc/run-live.ps1 -Slot 9 -Scenario e2e_mcp
powershell -File tools/pc/run-live.ps1 -Slot 9 -Scenario e2e_ghosts
powershell -File tools/pc/run-live.ps1 -Slot 9 -Scenario e2e_mining -TimeoutSec 900
powershell -File tools/pc/run-live.ps1 -Slot 9 -Scenario e2e_forge  -TimeoutSec 900
```

Итог — `results-<N>.json` в папке, которую печатает скрипт (или в `-OutDir`). Рядом: `live-<N>.log`
(конверты стенда), `factorio-<N>.log` (журнал игры без пароля), а у сценариев через сервер ещё
`server-<N>.log` и `calls-<N>.jsonl` (каждый вызов инструмента, без ключа и без строки чертежа).
Код выхода: 0 — прошёл, 1 — не прошёл, 2 — сбой стенда.

### Когда forge стоит на ноутбуке, а не на ПК

```powershell
$env:FP_FORGE = "<папка checkout'а factorio-forge на этой машине>"
powershell -File tools/pc/run-live.ps1 -Slot 9 -Scenario e2e_forge -Local -LocalPython <python 3.11+ с зависимостями сервера>
```

`-Local` исполняет сценарий на ноутбуке: игра по-прежнему на ПК, а её RCON пробрасывается
SSH-туннелем (`127.0.0.1` здесь ↔ `127.0.0.1` на ПК; наружу RCON не слушает). Одноразовый пароль
слота на время прогона копируется в папку результатов и удаляется в конце. Без `-Local` переменные
`FP_FORGE…` означают пути на ПК, с `-Local` — на ноутбуке.

## Как устроена проверка через настоящий сервер

Сценарий с `RUNNER = "server"` запускает не `live_client.py`, а `tools/pc/server_client.py`. Тот
поднимает настоящий `Core` из `server/factorio_partner` (те же `bridge.py`, `rcon.py`, `validate.py`,
`forge.py`, что у MCP-сервера) и зовёт его `op_*` — это ровно то, что стоит за инструментами
`partner_*`. Не проверяется только тонкий слой stdio из `server.py`.

- Ключ помощника создаётся на один прогон и в результаты не попадает.
- Для сверки сценарий может спросить мод и в обход сервера (обычным конвертом).
- В пакет стенда кладётся копия `server/factorio_partner/*.py` из репозитория, без правок.

## Честность предметов

Во всех сценариях помощник появляется с пустым инвентарём. Предметы — только так:

1. `collect` со складов рядом;
2. `find` по всей базе → `collect` с центром у найденных складов (помощник идёт сам); если издалека
   содержимое не видно — `walk` к складам и `collect` вокруг себя;
3. чего на складах нет — сырьё тем же способом и `craft` руками.

Рецепты сценарий знает только базовые и только как подсказку, что нести. Сколько крафтов выйдет на
самом деле, говорит мод. Не вышло — сценарий **красный**, а в результате лежит `missing` и
`missing_detail`: чего не хватило, что лежало в инвентаре, какой рецепт предполагался.

## Что проверяет каждый сценарий

### `e2e_mcp` — MCP-сервер с настоящим модом
`admin_hello`, `admin_spawn` → `partner_brief` → `partner_state` → `partner_map` (17×17, помощник на
карте) → `partner_find` (предмет, который точно лежит на складе) → `partner_act(walk)` и
`partner_wait` до `job_done` (помощник действительно сдвинулся и стоит у цели) → `partner_wait` без
событий (`timed_out`) → `partner_reflex` (поставить, снять, неизвестный тип — отказ) → отказы самого
сервера: чужой ключ (`access denied`), неизвестное действие и лишнее поле (`bad_args`), радиус сверх
границы (`limit`) — до мода они не доходят → сверка в обход сервера (очередь пуста, помощник жив,
`module_errors = 0`) → `admin_remove`.

### `e2e_ghosts` — призраки уже стоят
1. Выбирается лента, которая есть на складах базы.
2. Ищется свободное окно **на руде**, место подтверждает `build_blueprint {dry_run}`.
3. Ставятся призраки чертежа «два бура лицом к ленте» — так, как их оставил бы игрок рамкой: у
   помощника нет ни предметов, ни дронов, поэтому постановка кончается `no_items`, а призраки стоят.
4. `ghosts` показывает, что нужно; предметы добываются честно; `build_ghosts {area, mode: "hand"}`.
5. Сверка с картой, а не с ответом действия: призраков 0; появились ровно 2 бура (смотрят друг на
   друга) и 3 ленты; у помощника убыло ровно 2 бура и 3 ленты. Постройки, стоявшие рядом до сценария,
   в счёт не идут.

### `e2e_mining` — разметка по MPP
1. Бур, лента и столб выбираются по складам базы.
2. Ищется руда (`resources` по именам руд, кольцами до 400 клеток) и свободное окно на ней. Окно
   маленькое (до 6 буров): поручение на всё пятно — это сотни буров, руками их за прогон не собрать.
3. `plan_mining {dry_run}` → `plan_mining` → призраки; `ghosts` видит столько же, сколько сообщило
   действие.
4. Предметы честно → `build_ghosts` по `detail.area`.
5. Сверка («покрытие»): призраков 0; буров на карте столько, сколько обещала разметка; у каждого
   бура в области добычи есть руда; буры покрывают не меньше 60 % клеток руды окна (клетки сняты с
   карты до постановки призраков); ленты смотрят в заданную сторону; убыло ровно `need`.

### `e2e_forge` — чертёж из forge
1. `partner_plan {task: "mining", resource: {name, area}, options}` на окно 9×4 на руде (одна пара
   буров, лента, столбы).
2. Если forge ответил `supported: false` — сценарий красный, причина лежит в результате дословно
   (`forge.reason`, `outcome: "forge_unsupported"`). Сценарий forge не чинит и профили не трогает.
   Агент в такой ситуации просит хозяина поставить призраки — это путь `e2e_ghosts`.
3. Иначе: ответ сверяется с контрактом (поля, `direction = 0`, `anchor` в центре окна), затем
   `build_blueprint {plan, anchor, direction, dry_run}` — призраков столько же, сколько предметов в
   `items`. Сервер сам грузит чертёж в мод через `blob_put`; строку чертежа агент не видит.
4. Предметы честно → `build_blueprint {plan, …, mode: "hand"}`.
5. Сверка: всё построенное лежит **внутри окна, которое просили покрыть** (так проверяется привязка
   чертежа forge к месту), буры смотрят на ленту, убыло ровно `items`.

## Журнал игры: `log_must_not_match`

Ошибка внутри модуля или рефлекса мод не роняет: пишет строку в журнал игры и растит счётчик
`module_errors`. Чтобы такие ошибки не проходили молча, сценарий кладёт в результат поле
`log_must_not_match` — regex или список regex. После остановки сервера стенд читает вынесенный
(вычищенный от пароля) журнал, и если в нём есть подходящая строка — ставит `ok: false` и пишет
`log_check` с первыми совпавшими строками. Нет журнала или кривой regex — тоже красный. Сценарии
`e2e_*` запрещают `\[factorio-partner\] .* failed`.

## Что показали живые прогоны 2026-10-13

Сервер без окна, копия `Vulkan-Start-test`, Factorio 2.0.77, игроков онлайн 0.

- **Слияние Y + M ломало загрузку мода:** `plan_mining` регистрировался дважды (в списке действий и
  как «необязательный модуль»). Git конфликта не показал, а игра падала при загрузке сейва. В каждой
  ветке по отдельности тесты зелёные; после слияния юнит-тесты Lua это ловят (десятки красных с
  «registered twice»). Исправлено в `control.lua` этой ветки — при слиянии волны правку надо сохранить.
- **Призрак бура ставится только на руду, которую бур добывает.** На голой земле и на вольфраме
  `build_blueprint` отвечает про электрический бур `cannot_place` (и в `dry_run`, и на деле).
- Ближайшая к базе руда в сейве — вольфрам (нужен большой бур, на складах его нет). Сценарии сами
  уходят на уголь и кальцит в ~200 клетках.
- Готовых буров на складах базы нет нигде. Электрический бур честно крафтится руками (схемы, шестерни,
  пластины со складов); ленты и столбы — со складов.
- `walk` к центру группы складов из `find` может ответить `path_failed` (центр внутри постройки) —
  надёжнее `collect {center}`: он сам подходит к каждому складу.
- **forge на ПК** подключается (checkout и его `.venv` найдены), но чертёж не даёт: в нём нет ни одного
  профиля (`list-profiles`: «no profiles yet») и версия старая — нет команды `notes`. Ответы сервера:
  `partner_plan` → `supported: false`, «в forge нет активного профиля сейва; попроси хозяина
  активировать профиль»; `partner_brief` → `notes_missing` с текстом ошибки forge про `notes`.
  `e2e_forge` на ПК поэтому красный (`outcome: "forge_unsupported"`). Чтобы он позеленел, хозяину надо
  обновить forge на ПК, создать и активировать профиль сейва — сценарий и сервер этого не делают.
- **Путь «чертёж из forge» целиком работает** — проверено тем же сценарием в режиме `-Local` с
  настоящим forge ноутбука (активен профиль этого сейва): `partner_plan` дал раскладку 9×4 на угле
  (2 бура, 3 ленты, 4 столба), `anchor` — центр окна, `dry_run` — 9 призраков без пропусков, после
  честного сбора предметов `build_blueprint` построил все 9 ровно в запрошенном окне (51 с).
- `e2e_mcp` — 22 вызова инструментов за 4 с, все шаги зелёные; `e2e_ghosts` — 46 с; `e2e_mining` —
  87 с (6 буров, 8 лент, 2 столба на кальците, покрытие окна 100 %).

## Финал с игроком — чек-лист

Это единственная проверка с живым человеком. Здесь проверяется то, что стенд без окна не может:
урон, смерть, возрождение, тело второго игрока, чат и достижения.

**Перед началом**
- [ ] Сейв — `Vulkan-Start-test` (копия). Рабочий сейв не трогаем.
- [ ] В этом сейве до сих пор не вводилась ни одна консольная команда (иначе шаг про достижения
      ничего не покажет).
- [ ] Мод `factorio-partner` включён, тестовый `partner-test` выключен.
- [ ] RCON хоста из меню включён в `config.ini` (`local-rcon-socket` на `127.0.0.1`,
      `local-rcon-password`); пароль лежит в файле вне репозитория.
- [ ] Заданы `FP_RCON_PORT`, `FP_RCON_PASSWORD_FILE`; ключи помощников — в `FP_HOME/helpers.json`.

**1. Хост из меню**
- [ ] Игрок: «Мультиплеер → Хост сохранённой игры» → `Vulkan-Start-test`.
- [ ] `'{"tool":"admin_hello"}' | python -m factorio_partner.cli --admin` — мод отвечает, `owner` —
      игрок, `players_online: 1`.
- [ ] Игрок отвечает, сколько помощников разрешает; запуск:
      `python -m factorio_partner.cli --helpers 1 --body character --helper h1`.
- [ ] Рядом с игроком появился второй персонаж с пустым инвентарём.

**2. Поручение в чат**
- [ ] Игрок ставит рамку MPP на руду (или чертёж буров) и пишет в чат: «поставь добычу здесь».
- [ ] Агент получил `player_said` с `owner: true`, ответил в чат (`h1: …`).
- [ ] Помощник сам собрал предметы со складов (или скрафтил) и построил призраки. Ничего не
      появилось из воздуха, помощник нигде не телепортировался — игрок это видит глазами.
- [ ] Второй раз — без рамки: «размечай сам» (`plan_mining`) на другом куске руды.
- [ ] Если подключён forge с активным профилем сейва — третий раз через `partner_plan`.
- [ ] Игрок нажал паузу / вышел в меню: агент получает `game_paused` и ждёт, а не ломается.

**3. Кусаки: отход, смерть, возрождение**
- [ ] Агент поставил рефлексы `flee` и `watch` (`partner_reflex`).
- [ ] Игрок приводит кусак к помощнику (или помощника отправляют к гнезду).
- [ ] `watch`: в событиях есть `saw_enemy`.
- [ ] `flee`: помощник бросил задачу и уходит; пришли `attacked`, `reflex_fired`, потом `reflex_done`.
- [ ] Помощника дали убить: пришли `job_failed {no_helper}`, затем `died {pos, corpse}`; на земле труп
      с вещами.
- [ ] Через 10 секунд — `respawned`; новое тело у точки появления, инвентарь пуст.
- [ ] Помощник дошёл до трупа и забрал вещи (`pickup`).
- [ ] `admin_hello`: `module_errors` не вырос.

**4. Тело второго клиента (`--body player`)**
- [ ] Второй клиент игры подключился к хосту под другим именем, у него есть персонаж.
- [ ] `python -m factorio_partner.cli --body player --helper h2 --player <имя второго игрока>`.
- [ ] Помощник `h2` ходит и строит телом второго игрока: `walk`, `collect`, `build_ghosts`.
- [ ] Игрок за вторым клиентом шевелит мышкой и клавишами — ходьба и добыча помощника не срываются.
- [ ] Второй клиент вышел: `job_failed {no_helper}` и `helper_lost {reason: "player_left"}`; вернулся —
      тело подхватилось снова.
- [ ] `helper_remove` для `h2` только отвязывает: персонаж второго игрока жив.

**5. Достижения — в самом конце**
- [ ] Игрок **один раз** вводит в чат `/c game.print(1)`.
- [ ] Игра показывает предупреждение, что консольные команды отключат достижения. Значит, до этой
      минуты достижения были включены: всё, что делал напарник, их не тронуло.
- [ ] Команду **не повторять** и сейв после этого шага не сохранять поверх рабочего.
- [ ] Предупреждения нет (команда сразу выполнилась) — достижения уже были отключены. Это провал
      проверки: искать, кто отправил консольную команду.

**После**
- [ ] Журнал игры: нет строк `[factorio-partner] … failed`.
- [ ] Итоги записать в `research/` (без личных путей, имён и адресов).
