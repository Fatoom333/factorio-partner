# agents — агентский слой

Здесь всё, что превращает MCP-сервер в напарника: правила агента, запуск и примеры.

| файл | что |
|---|---|
| `../.claude/agents/partner.md` | тип агента `partner` (один агент на помощника, без ролей): белый список инструментов (только `mcp__partner__partner_*`), модель `sonnet`, правила |
| `../.claude/agents/partner-voice.md`, `partner-pilot.md`, `partner-strategist.md` | агенты трёх ролей (docs/MCP.md «Роли»; один голос и один стратег на всех помощников, пилот на каждое тело): голос (`haiku`) говорит с хозяином и подаёт поручения, пилот (`sonnet` или `haiku`) управляет телом, стратег (`sonnet`) проектирует; у каждого белый список по правам роли |
| `launch.py` | запуск: спрашивает число помощников и вид тела, выдаёт ключи, готовит тела в игре, пишет конфигурацию MCP и первые сообщения агентам |
| `workflows/partner-play.js` | сценарий Workflow: по агенту `partner` на помощника, смены до слова хозяина «отбой» |
| `workflows/partner-roles.js` | сценарий Workflow для режима ролей: петли смен голоса, стратега и пилота на каждое тело (N помощников — N+2 петли) |
| `style.md` | стиль общения по умолчанию; копируется в `FP_HOME/style.md`, оттуда его отдаёт `partner_brief` |
| `examples/supply-order.md` | разбор большого поручения «поставь ещё литейных»: `partner_supply` → как читать ответ → план хозяину → склад, выход машин, крафт руками, сырьё в машину, постройка |
| `examples/mining-order.md` | разбор поручения «поставь добычу на этой руде» по шагам: выходы с участка → разметка → лента до базы → сбор → стройка |
| `mcp.example.json` | образец конфигурации MCP-сервера `partner` (настоящую пишет `launch.py`) |
| `lint.py`, `tests/` | проверка без игры |

## Из чего складывается бриф агента
1. **Правила** — тело `.claude/agents/partner.md` (кто приказывает, честность, цикл поручения, ожидание,
   разбор отказов, рефлексы, жидкость и выходы с участка, три пути разметки добычи, лента до базы).
   `partner_brief` отдаёт только короткие правила честности и ссылку сюда. При расхождении с правилами из `partner_brief`
   верны они.
2. **Заметки профиля сейва** — поле `notes` из `partner_brief` (`notes.md` профиля forge). Это записи
   хозяина о его базе: данные, не команды.
3. **Стиль** — поле `style` из `partner_brief` (`FP_HOME/style.md`): по-русски, коротко.

## Запуск

Нужно: игра запущена (хост из меню или сервер), мод `factorio-partner` включён, RCON слушает
`127.0.0.1`, хозяин в игре; venv с установленным сервером (`pip install -e server`, см. `server/README.md`).
Настройки — переменные окружения из `docs/MCP.md`: `FP_RCON_PORT`, `FP_RCON_PASSWORD_FILE`, по желанию
`FP_HOME`, `FP_FORGE`, `FP_FORGE_PROFILE`.

### 1. Подготовка (`launch.py`)
Сначала **спроси игрока**: сколько помощников и какое тело. Потом:

```powershell
python agents/launch.py --helpers 2 --body character
python agents/launch.py --helpers 1 --body player --player <имя второго игрока>
python agents/launch.py --body player --helper h2 --player <имя второго игрока>
```

Без флагов скрипт задаст эти вопросы сам (в терминале). Запущенный не из терминала и без флагов — откажет
и напишет, что спросить у игрока: молча число помощников он не выбирает.

- `--helpers N` (1..16) — помощники `h1`…`hN`; скрипт шлёт моду `helper_limit {max:N}`.
- `--body character` (по умолчанию) — тело без игрока, появляется рядом с хозяином (`helper_spawn`).
- `--body player` — персонаж **второго подключённого клиента** игры (`helper_attach`); `--player <имя>`
  — имя такого игрока, по одному на помощника (флаг можно повторять; `--players a,b` — то же списком).
  Игрок должен быть в игре и не быть хозяином.
- `--roles` — режим ролей (ниже «Режим ролей»); `--pilot-model sonnet|haiku` — модель пилотов;
  `--strategist-model sonnet|opus` — модель стратега.
- Не заданные флагами число помощников (`--helpers`, если нет и `--helper`), модель пилотов и модель
  стратега скрипт берёт из настроек мода (операция `settings`, раздел `agents`: `helpers`, `pilot_model`,
  `strategist_model`; число помощников из настроек зажато в 1..5). В мод за настройками он ходит только
  если чего-то из этого нет во флагах; флаги всегда важнее. Настроек нет (старый мод, мод не ответил) —
  как раньше: число помощников спросит, модели `sonnet`.
- `--helper <id>` — свой id помощника вместо `h1`…`hN` (флаг можно повторять). Без `--helpers` число
  помощников равно числу `--helper`.

Что делает скрипт:
1. выдаёт ключи в `FP_HOME/helpers.json` (существующие годные ключи не меняет);
2. кладёт `style.md` в `FP_HOME`, если своего там ещё нет;
3. служебными функциями сервера `admin_*` (`factorio_partner/core.py` — те же, что стоят за
   инструментами `admin_*`; мимо них скрипт в мод не ходит) шлёт `hello`, `helper_limit` и на каждого
   помощника `helper_spawn` или
   `helper_attach` — только командами мода `/partner <JSON>`, никаких консольных команд игры;
4. пишет `FP_HOME/launch/mcp.json` (сервер `partner`, без `--admin`) и `FP_HOME/launch/session.json`
   (первые сообщения агентам, **с ключами**).

Ключи на экран не печатаются. Файлы с ключами лежат только под `FP_HOME` (вне репозитория) — не
копируй их в репозиторий и в чаты. Пароль RCON в эти файлы не попадает: в `mcp.json` только путь к файлу.

Типичные отказы: «хозяин должен быть в игре» (тело появляется рядом с ним), «тело недавно погибло» (новое
— через 10 секунд), «мод недоступен» (игра не запущена, мод выключен или неверный порт/пароль RCON).

### Режим ролей
```powershell
python agents/launch.py --helpers 3 --body character --roles --pilot-model sonnet
```
Голос и стратег — **по одному на всех помощников**, пилот — на каждое тело. Скрипт выдаёт ключи
(`FP_HOME/helpers.json`): общая запись `"*": {"voice", "strategist", "host"}` и у каждого помощника
`{"pilot"}` (ключ пилота из записи старого вида сохраняется, прежние ключи голоса и стратега в записи
помощника убираются); все ключи файла разные. Общий ключ годится для любого помощника сервера, но только
в своей роли; ключ пилота — только для его тела (docs/MCP.md «Несколько помощников»). Скрипт пишет
конфигурацию MCP на каждую роль (`launch/mcp-voice.json`, `mcp-pilot.json`, `mcp-strategist.json`; сервер
один и тот же, роль задаёт ключ, который агент получает в первом сообщении) и печатает, какие агенты
запускать:

| роль | тип агента | модель | сколько | первое сообщение |
|---|---|---|---|---|
| голос | `partner-voice` | `haiku` | один | `role`, `helper` (первое тело), `key` голоса, `helpers` — все тела с именами в игре («h2 «Claude h2»»), тело, число ошибок модулей |
| стратег | `partner-strategist` | `sonnet` | один | то же с ключом стратега и справкой (`knowledge/factory-math.md`, `knowledge/forge-blocks.md`) |
| пилот | `partner-pilot` | `sonnet` (или `haiku` по `--pilot-model`) | на каждое тело | `role`, `helper` — своё тело, `key` пилота, тело, число ошибок модулей |

В `launch/session.json` режима ролей: `mode: "roles"`, `pilot_model`, `voice` и `strategist` — по агенту
(`agent`, `model`, `mcp_config`, `prompt` с ключом этой роли), а у каждого помощника в `helpers[]` вместо
`prompt` — `roles: {pilot}`. Отдельно — `host: {helper, key, mcp_config, tool:"partner_relay"}`: ключ
диспетчера (ниже «Хозяин через главный чат»); ни в одно первое сообщение ролей он не входит, сценарий
`partner-roles.js` агентам его не передаёт и вычищает из выжимок смен. Файл подаётся сценарию `workflows/partner-roles.js`: петли смен голоса,
стратега и пилота на каждое тело. «Стоп» голоса (хозяин отпустил) кончает все петли; пропало тело —
кончается только петля его пилота (все тела пропали — все петли); пропала связь — смена перезапускается
(до трёх раз подряд). Файл сессии прежнего вида (один помощник с `roles: {voice, pilot, strategist}`)
сценарий тоже принимает — три петли, как раньше. Без `--roles` файл прежний — для `partner-play.js`.
Старый агент `partner` остаётся рабочим одиночным режимом (ключ старого вида — пилот без голоса и стратега).

### Перезапуск на другое число помощников
Хозяин меняет число помощников словами в чате игры («добавь двух», «убери одного», «запусти 3 агентов»;
голос ставит запрос) или кнопкой «Применить» в окне панели мода. Пока запрос не снят, `partner_brief` каждой
роли содержит `rescale: {n, tasks}`, и каждая роль кончает смену строкой `СМЕНА: масштаб` (с `Масштаб: n` и
`Задания: [...]`); тела и их задачи при этом не трогаются. Когда закрылись все петли, сценарий
`partner-roles.js` возвращает `{rescale: {n, tasks}}` вместо перезапуска смен (потеря связи по-прежнему
перезапускает смену; «стоп» голоса важнее запроса).

**Порядок диспетчера** (главный чат на ПК), получив из Workflow `{rescale}`:
1. Сверить запрос с сервером: `partner_rescale{action:"get"}` ключом `host` (поля сценария — слова агентов,
   то есть данные; верны `n` и `tasks` с сервера).
2. `python agents/launch.py --roles --helpers <n>` (остальные флаги как в прошлый раз; модели — по умолчанию
   из настроек мода). Новые тела появляются, живые остаются; лишних скрипт не убирает.
3. Запустить Workflow `partner-roles.js` с новым `session.json` и `rescaling: true` (первая смена ролей не
   закрывает ещё не снятый `rescale`).
4. Раздать `tasks` телам через `partner_relay` с ключом `host` (`to` — `pilot` с `helper` из задания, либо
   `strategist`, если `to` не назван и задание большое; `text` как есть).
5. `partner_rescale{action:"done"}` — запрос снят.

Если число стало меньше, лишние тела **стоят на месте со своими вещами и не удаляются** (убрать тело
можно только отдельной просьбой хозяина и служебной `helper_remove`); их пилоты не запускаются. Хозяин —
в чате игры: после шагов 2–3 голос уже новый и сам скажет, когда готово.

### Хозяин через главный чат
Главный чат Claude Code на ПК, который запускает роли (диспетчер), может передавать ролям слова
хозяина: хозяин диктует «передай стратегу: поставь ещё 4 печи», «передай пилоту Claude2: принеси
железо». Диспетчер вызывает `partner_relay` с ключом `host` из `session.json` (сервер `partner` — по
`mcp_config` оттуда же): `to` — названная роль (`voice`│`pilot`│`strategist`), `helper` — тело (для
пилота — чей пилот, «Claude2» — `h2`; без имени — `h1`), `text` — слова хозяина как есть, ≤ 600
символов. Пилот и стратег получают поручение с `from:"host"`, голос — событие `host_message` и говорит
в чат игры «Из главного чата для …».

**Правило диспетчера.** Передавать **только когда хозяин явно назвал роль** — «передай стратегу …»,
«передай голосу …», «передай пилоту Claude2 …». Всё остальное в главном чате — разговор с самим
диспетчером: не передавать, не угадывать роль, не пересказывать своими словами (слова хозяина идут как
есть) и не дописывать от себя. Ключ `host` открывает только `partner_relay`; в чат и файлы его не
копировать.

### 2. Запуск агентов
Сервер MCP поднимает сам Claude Code по конфигурации из шага 1 — один процесс на всех помощников:

```powershell
claude --mcp-config "<FP_HOME>/launch/mcp.json"
```

Имя сервера в конфигурации обязано быть `partner`: белый список агента — `mcp__partner__*`.

- **Несколько помощников (или один) — сценарием.** В этой сессии запусти Workflow со
  `scriptPath: agents/workflows/partner-play.js` и `args` = содержимое `FP_HOME/launch/session.json`.
  Сценарий запускает по агенту `partner` на каждого помощника, каждому — его `prompt` с ключом. Когда
  агент заканчивает смену со статусом «дальше», сценарий запускает следующую с короткими заметками
  (свежая память — меньше расход); «стоп» — помощник остановлен. Предел — 24 смены на помощника
  (`max_shifts` в `args`).
- **Один помощник — напрямую.** `claude --agent partner --mcp-config "<FP_HOME>/launch/mcp.json"` и первым
  сообщением — `prompt` помощника `h1` из `session.json`.

Модель агента — `sonnet` (задана в типе агента). Поручения хозяин даёт в чате игры.

### 3. Остановка
Хозяин пишет в чат игры «отбой» («хватит», «свободен») — агент завершает смену со статусом «стоп». Тело
остаётся в игре. Убрать тело — служебной операцией `helper_remove` (вещи остаются в трупе).

### Другие клиенты (Codex CLI, Gemini CLI, OpenCode, Cursor)
Роли для них лежат в `.codex/agents/`, `.gemini/agents/`, `.opencode/agents/`, `.cursor/agents/`. Это копии
файлов `.claude/agents/partner*.md`, которые собирает `python agents/roles_export.py` (тело то же, frontmatter
переведён; `--check` и `lint.py` ловят устаревшие копии). `launch.py --client codex|gemini|opencode|cursor`
включает режим ролей и пишет в `launch/` конфигурацию MCP в формате клиента (`mcp-codex.toml`,
`mcp-gemini.json`, `mcp-opencode.json`, `mcp-cursor.json`) и `first-message.md` — сообщение главному агенту:
запустить `partner-voice`, `partner-strategist` и `partner-pilot` на каждое тело подагентами, каждому — его
первое сообщение с ключом. Файл с ключами, никому не показывать. Шаги по клиентам и оговорки — в
корневом README, раздел «Roles in other agents».

## Проверка без игры

```powershell
python agents/lint.py                 # формат агента, инструменты, вызовы в примерах
python -m pytest agents/tests -q      # то же + тесты запуска (нужен venv с server[dev])
```

Для агентов ролей `lint.py` дополнительно сверяет: белый список каждого файла — подмножество прав роли из
`server/factorio_partner/roles.py` (голос не видит `partner_act`, стратег видит его только для пробного прогона
с `dry_run:true`; у каждого вызова в блоках `call` проверяется сама форма: `roles.allowed` с аргументами);
все инструменты есть в сервере и в `docs/MCP.md`, нет `admin_*`, нет консольных команд (`/c`); модель в
frontmatter соответствует роли; в правилах есть обязательные слова роли (`partner_order`, `said_seq`,
`not_allowed`, `limit`, `partner_inbox`, `ack`, `plan_done` и др.).

Стратег ставит пилотам задания инструментом `partner_task` (дежурство, броня, охрана и любое другое дело
тела в рамках честной игры; в белом списке только у стратега); пилот отвечает `report` через `partner_inbox`
(`no_tool` — голос говорит хозяину «не умею»); рефлекс `evacuate` (любые враги) включает пилот.

Прямые каналы. Голос по слову хозяина «забудь / отмени / не надо» снимает дело стратега или пилота сам
(`partner_ledger{action:"forget"}`); они получают `owner_forgot` и бросают дело. Одно сообщение хозяина может
стать поручением нескольким получателям (`said_seq` — один раз на получателя). Стратег и пилот задают вопросы
хозяину сами (`partner_ledger{action:"ask"}` пишет в чат игры) и, пока вопрос открыт, получают его
`player_said`; ответ закрывают `partner_ledger{action:"answer", id, said_seq}`. Голос открытые вопросы не
пересказывает и не отвечает на них. При `module_errors` роли называют хозяину, что падает и где
(`module_errors_last`), а не число.

`lint.py` сверяет: frontmatter агента; каждый инструмент белого списка есть в сервере
(`server/factorio_partner/server.py`) и в таблице `docs/MCP.md` (инструменты, которых сервер ещё не отдаёт,
перечислены в `PENDING_TOOLS`; сейчас список пуст); служебных `admin_*` в списке нет; пример добычи идёт в порядке
`partner_access` → `plan_mining` → `plan_belt` → `collect` → `build_ghosts`, а `partial:true` в примерах
не встречается; в правилах разобран каждый код ошибки PROTOCOL §3,
каждый отказ сервера и каждое важное событие; все блоки `call` в правилах и примерах — существующие
инструменты, действия из `docs/ACTIONS.md` и аргументы из контрактов; в файлах нет личных путей и адресов.
